# 配图图注契约 v1（2026-10-25）

> 一句话：**识图不在剪藏请求里做**。剪藏只留占位符，蒸馏前再补图注。

---

## 0. 为什么要改（问题不是"锦上添花"，是用户在转圈）

识图 = 下载正文里的每张图 + 调 VLM 认字。实测（生产 8.148.9.151，14 张正文图的公众号文）：

| 环节 | 实测 |
|---|---|
| 下载 14 张（并发 4） | 4.0s |
| 认图 14 张（并发 3） | 17.4s |
| **整篇剪藏（原来）** | **22.8~30.8s**（30s 抓取预算被吃干） |

而剪藏是**同步接口**、用户在手机上盯着转圈。内测反馈的「剪藏一直不成功」
一半就来自这里 —— 30s 几乎必然被用户当成"坏了"。

⇒ 改成两段：

```
剪藏请求            → 只抓正文，正文里留占位符 + 图清单落库     （目标 < 5s）
   ↓（用户立刻看到"剪藏成功"）
蒸馏任务（后台）    → 蒸馏前调 content-service 内部端点补图注
   ↓
                    → 正文里的占位符换成图注文字 → 喂给 LLM
```

## 1. 占位符的**两种形态**（唯一真相源：`common/media_placeholders.py`）

| 形态 | 样子 | 用在哪 | 为什么 |
|---|---|---|---|
| **内存态** | `\x00IMG3\x00`（真 NUL） | 解析阶段、正文里定位 | 正常文字里不会出现 NUL ⇒ 不会和真实内容碰撞 |
| **落库态** | `\x00IMG3\x00`（可见记法） | PostgreSQL JSONB | JSONB **不接受** `\u0000`（实测 `unsupported Unicode escape sequence`） |

⚠️ **落库形态必须可逆**：文章是**带着占位符先落库**、之后才补图注 ⇒
补图注时要拿内存态的 token 去匹配正文里的位置。

⇒ 这份契约被 content-service 与 ai-service 同时依赖 ⇒ 放在 `common/` 下
**只有一份实现**。两边各写一份正则，就会只改到一半。

### ⚠️ 最阴的退化：占位符认不回来

`_strip_nul`（FetchResult → JSONB）会把所有 NUL 删掉 ⇒
`\x00IMG3\x00` 变成裸的 `IMG3` ⇒ **再也认不回来** ⇒
补图注匹配不到位置 ⇒ 图表信息**静默消失**，而正文看着还挺正常。

⇒ 落库前必须先把占位符换成可见记法（`to_storage_text`），
**再**走剥 NUL。判据由 `tests/content/test_caption_fill_endpoint.py::
test_落库时占位符不被剥成裸_img` 锁住。

## 2. 职责边界

| 环节 | 谁做 | 为什么是它 |
|---|---|---|
| 抓正文、留占位符 | content-service 的 fetcher | 它本来就抓 |
| 下载图 + 认图 | content-service（`caption_stored_content`） | 下载要走**它那套** SSRF 防护、按 host 节流、池化 client + 按画像的 header。搬到 ai-service 就是复制第二份 ⇒ 两份各自漂移 |
| 把图注写回 `articles.raw_content` | content-service | 那张表是它写的（剪藏时它写的） |
| 什么时候补 | ai-service 的蒸馏任务 | 蒸馏之前、LLM 之前 ⇒ 图注能进稿子 |
| 兜底剥占位符 | ai-service（`strip_placeholders`） | 绝不让占位符进 LLM 的 prompt |

## 3. 接口

### 3.1 `POST /api/v1/internal/articles/{article_id}/captions`（content-service）

* **鉴权**：`X-Callback-Secret` 共享密钥，**fail-closed**
  （没配密钥 = 503，不是放行）。
  理由很硬：未鉴权的话，任意匿名请求就能让本服务下载任意图片、
  调任意次数的 VLM ⇒ 直接烧钱。
  ⚠️ 环境变量名是 **`CALLBACK_SHARED_SECRET`**（`common/config.py` 没有 `env_prefix`，
  名字就是字段名的大写）。
* **幂等**：补完就删掉 `media_refs` ⇒ 再调一次是 no-op（**不会重复烧 token**）。
* **失败**：一律返回 200 + `captions: 0`。识图失败只意味着"这篇没有图表信息"，
  正文照常蒸馏 —— 不能因为可有可无的图表把整篇文章的稿子赔进去。
* **超时**：端点内部认图预算 90s（`STASHBOX_CAPTION_FILL_BUDGET` 可覆盖）；
  调用方 ai-service 的 HTTP 超时 120s。

### 3.2 `services/content_client.py`（ai-service）

`fill_article_captions(article_id) -> int` —— 返回补上的图注条数。
**所有失败都降级成 0**，不抛异常。

## 4. 幂等与降级的完整链路

```
剪藏            → raw_content = { content_text: "…\x00IMG1\x00…",        ← 落库态
                              raw_metadata: { media_refs: [...] } }
蒸馏前补图注    → raw_content = { content_text: "…图表：一季度增长 30%…", ← 落库态（占位符已被替换）
                              raw_metadata: { media_captions: [...] } }   ← media_refs 已消失
再调一次        → no-op（没有 media_refs ⇒ 立刻返回 0）
补图注失败      → ai-service 兜底 `strip_placeholders` ⇒ 正文里不留占位符，照常蒸馏
```

⚠️ **失败图的占位符是直接删掉的**（不留"（图片识别失败）"这种噪声），
原因记在 `media_captions[].error` 里 —— "这篇为什么没有图表信息"查得到原因。

## 5. 识图的既有约束（未变）

| 约束 | 值 | 依据 |
|---|---|---|
| 每篇最多识**不同图 URL** 数 | 12 | 生产 33 篇里 22 篇（67%）图数 > 5；旧上限 5 让三分之二的文章白丢图 |
| 单图下载上限 | 2MB | 缩图后 ~250KB；5MB 会让下载阶段同时攥着 7 张原图 |
| 单篇下载字节总预算 | 8MB（**软上限**，实际 ≤ 8MB + 4×2MB = 16MB） | 内存上界与文章有多少张图解耦 |
| 下载并发 / 识图并发 / 全进程识图并发 | 4 / 3 / 6 | 实测 provider 并发 6 零失败零限流 |
| 补位轮 | 最多 1 轮，总尝试 ≤ 2×上限 | 防止"无限往下翻图" |
| 零信息判失败 | OCR **明确声明**"图里没有文字" | 启发式会误杀真有文字的图 |

## 7. 已知遗留（架构级）

识图整体搬到 arq worker（让 content-service 自己起 worker 跑识图任务，
而不是 ai-worker 跨服务 HTTP 调过来）会更干净 —— 那样 content-service
的 HTTP 线程就不碰 VLM 调用。

本轮没做：跨服务 HTTP 这一步多了一次网络往返和一次跨进程失败模式
（content-service 挂了 ⇒ 这篇没有图注，但正文照常蒸馏）。
**代价可接受，收益（少一次跨服务调用）不急。**
