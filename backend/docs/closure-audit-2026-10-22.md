# 全工程功能闭环走查（2026-10-22）

## 方法：三层证据，不靠印象

「功能闭环」不是一个能靠读代码读出来的东西，必须分层验证：

| 层 | 手段 | 能发现什么 | 发现不了什么 |
|---|---|---|---|
| ① 静态差集 | 抽客户端实际调用的 (method, path)，与后端路由表/openapi 求差集 | 客户端调了但服务端根本没有 | 端点在、但一调就 500 / 鉴权挂了 / 响应结构对不上 |
| ② 真链路冒烟 | 在**生产**上把每个端点**真的调一遍** | 端点在但跑不通、鉴权失效、参数契约不符 | 代码里的逻辑漏洞（点了没反应、状态不更新） |
| ③ 代码走查 | 逐个功能点看「UI → ViewModel → Repository → API → 状态 → 反馈」 | 死按钮、被吞的异常、状态不更新 | 运行时才暴露的问题 |

**① 的两个坑（都踩过）**：
- **清单不能手写**。第一版冒烟脚本里我凭印象写了 `GET /api/v1/users/me/onboarding`，
  而安卓端真实定义的是 `POST /api/v1/users/me/onboarding/start|step|done` ——
  手写的那条报 404，看起来像断链，**其实客户端根本没调过它**。
  → 清单必须从代码自动抽取（`scripts/client_endpoints.json`，由 Retrofit 注解 +
  admin-web 的 `apiClient.METHOD()` 抽取而来），并随代码一起进仓库。
- **端点「在」不等于「通」**。本轮 44 个 admin-web 端点里，只有 20 个返回 200；
  其余是 422（参数校验）、400（业务校验）、404（参数指向不存在的对象）——
  **全都不是断链**，端点都在、鉴权都在。

**② 的一个坑**：网关把「鉴权头缺失」也兜底成 **502「暂时连不上后端服务」**。
本轮一度以为是「admin 路由全挂」，其实只是我的脚本把 admin 登录返回的
**顶层** `access_token`（没有 `data` 包装）取错了位置 → token 为空 →
所有 admin 请求都是无鉴权的 → 被兜底成 502。
→ **看到 502「连不上后端」先确认 token 拿到了**，那是鉴权问题，不是服务挂了。

## 结果

### ① 静态差集

| 客户端 | 端点数 | 服务端没有的 |
|---|---|---|
| 安卓（Retrofit） | 54 | `GET /api/v1/auth/me`、`POST /api/v1/auth/logout` |
| admin-web | 44 | 0 |

- `GET /api/v1/auth/me`：**死接口** —— 定义在 `AuthApi.kt`，全项目无人调用。
- `POST /api/v1/auth/logout`：**服务端没有这个端点** → 客户端 logout 永远拿不到
  「服务端已吊销 token」的确认。客户端靠 `catch (_: Exception)` 兜住 404 并
  照样清本地状态，**登出功能本身不受影响**；但**服务端 token 不会被吊销**
  → 设备丢失/凭据泄露时，已登出的会话在服务端仍然有效。**这是安全缺口**。

## 缺口清单（按严重性）

### 🔴 P1：服务端缺 `POST /api/v1/auth/logout` → token 无法吊销

客户端的「退出登录」只清了**本地** token 与本机数据，服务端的 token 仍然有效。
设备丢失、或用户以为登出了却没登出时，服务端会话可继续被使用。
**修法**：user-service 加该端点（吊销 token，落 `common/revocation.py`），
网关 Route 表加一行；客户端的 `catch` 保留（幂等，不阻塞本地登出）。

### 🟡 P2：`GET /api/v1/auth/me` 是死接口

`AuthApi.kt` 里定义了，全项目无人调用，服务端也没有。
**修法**：删掉客户端定义（连带响应体类型），或服务端补齐端点。
现状是**无害的死代码**，但它让「客户端调了服务端没有」的差集检查永远不干净。

### 🟡 P3：客户端与后端的端点契约没有自动化守卫

今天这类问题要靠人工比对才发现。**修法**：
- `scripts/client_endpoints.json`（已进仓库）= 客户端调用的端点快照；
- `scripts/endpoint_smoke.py`（已进仓库）= 生产环境逐个真调的冒烟脚本；
- 建议加进 CI：端点清单变化时提醒同步契约。

## 本轮同时修掉的（不属于走查，但被走查牵出来）

1. **备案未过 → 大流量分发走 IP**：域名入口的 `/downloads/` 统一 302 到 IP
   （实测未备案域名在 443 上小请求正常、大流量被掐），应用内更新下载地址也改 IP。
2. **访问日志加上 `host` 与服务端耗时**：内置 combined 缺这两个字段，
   导致「下载慢」只能猜是服务器慢还是链路慢 —— 先怀疑了用户网络、
   又怀疑了服务器负载，两个都是被这个缺口逼出来的弯路。
3. **dev 登录 code 按设备恒定**（`ANDROID_ID` 派生）：同一台手机重装/清数据
   之后还是同一个 uid，users 表不再因为「重装一次」而膨胀。
4. **注销过的账号不能登录**（原来只按 open_id 查、没过滤 `deleted_at`）：
   注销后用旧 code 再登录会**建新号** → 清理完一登录又长回来。
5. **抓取失败话术按抓取器分流**：PDF 返回 403 时用户看到的是
   「微信文章请在微信里打开后重新复制链接」—— 对着一个 PDF 说这句话。

## 一、admin-web 的 2 个真断链

### 1. 「失效音频」按钮对**所有**文章永久禁用 🔴

admin-web 用 `article.audio_id` 判断「这篇文章有没有关联音频」，
失效端点 `POST /api/v1/admin/audio/{audio_id}/invalidate` 做的是
`db.get(DistilledArticle, audio_id)` —— 要的是**蒸馏结果的主键**（`dst_xxx`）。

而列表端点 `GET /api/v1/admin/articles` 只下发 `audio_url`（OSS URL 字符串）。
两者不是一回事 → `hasAudio` 恒为 false → **每一行的「失效音频」按钮都是灰的**，
这条功能从头到尾没被用过。

**修**：列表端点把蒸馏结果的主键一起下发（顺带把 `tags` / `quality_score`
也带上 —— 后台文章表有这两列、按数据决定显隐，而列表端点从来没下发过，
两列永远不出现，契约是一句空话）。

**实测**：列表现在返回 `audio_id='dst_ea754418f6a74af5964a4db8'`。

### 2. 6 处写操作在「网关不可达」时完全无提示 🔴

响应拦截器只在**有 HTTP 状态码**时才 toast。网关不可达 / 跨域失败 /
axios 超时，axios 交给拦截器的 error 里**没有 response** → `status` 是
`undefined` → 三个分支全不命中 → **一个字都不弹**。

于是这 8 处 catch 里的注释「拦截器已 toast」是**假的**：
发起盲测 / 提交评分 / 提交标注 / 重推 / 保存 tier / 池清理 / 抽查回写。
用户视角：网关一挂，点「发起盲测」→ 按钮转一圈恢复原状，界面毫无变化。

**修**：在拦截器里统一补 `status === undefined` 分支（一次改，所有写操作受益）。
同时把「无法连接 api-gateway（localhost:8100）」里的硬编码地址去掉 ——
生产构建的 baseURL 是同源，写死 localhost 会让运维去查一台根本不存在的机器。

## 二、后端与部署的 4 个真断链

### 3. 登出只杀了 access token，refresh 那条腿还活着 🔴

**这是本轮最要紧的一条，而且是我自己上一个 commit 引入的假闭环。**

logout 端点刚补上时，我实测过：登出后 access token 立刻 401
「Token has been revoked」。但拿**同一个 refresh token** 去换新 token
依然返回 **200** —— refresh 端点只查 `users.deleted_at`，**从不看吊销标记**。

后果：设备丢了、用户以为登出了，旧 refresh token 最长 30 天内能无限换出
新 access token —— 等于给用户发了一张「已登出」的假凭证。

**修**：
- refresh 端点补吊销检查（与 `require_user` 同一套判据）；
- 吊销判据从秒级提到**毫秒级**：JWT 的 `iat` 只有秒精度
  （python-jose 3.5.0 编码时按 `utctimetuple()` 截断），拿它去比一个带
  小数秒的边界就分不出同一秒内的先后 —— 严了会误杀「登出后立刻重新登录」
  的新 token，宽了会让旧 token 活满 7 天。token 里多带一个 `iat_ms`
  毫秒戳，两个错都不用犯；
- 吊销边界按 `ms:` 前缀存 —— 值自己说明刻度，不靠数值大小猜
  （这个改法是被测试逼出来的：第一版靠「小于 1e11 当秒」猜刻度，
  测试一换非当代时刻就判错，边界差 1000 倍）。

**实测**（生产机）：

    登出后 access token:  HTTP 401  Token has been revoked
    登出后 refresh token: HTTP 401  Token has been revoked
    登出后重新登录可用:   HTTP 200

### 4. `POST /api/v1/users/me/quota/reset-monthly` 在网关是 404 🔴

实现一直在 user-service 里，也进了 OpenAPI 契约，但**没进路由表** →
走兜底时首段 `users`（复数）不在白名单 → 网关直接 404「接口不存在」。

**实测（修复前）**：网关 404，直连 user-service 才是 401。

`api-gateway/config.py` 的注释里记着**同款事故的三次**
（`notifications/{id}/mark-read`、`admin/export/tags.csv`、`admin/llm/*`），
这次是**第四例**。

**修**：
- 补路由；兜底白名单补 `users`（显式路由表先匹配，命中不了的才走兜底，
  猜不到就是 404。宁可通到下游让它自己答 404/401，也不要网关替下游撒谎）；
- 剪藏与重试这两个**最核心的写端点**从兜底提到显式注册 ——
  原来靠前缀猜下游，猜对了，但兜底路径不注入 `X-Request-ID`，
  两边日志串不上号，而「剪藏失败要回溯扣费与蒸馏派发」恰恰最需要串号；
- 兜底路径也补 `X-Request-ID`：同一个网关不该有两套链路串联口径；
- **新增路由一致性守卫**（`tests/gateway/test_route_coverage.py`）：
  路由表每条都要有下游实现，且下游每个端点网关都要路由得到。
  这条测试能挡住下一例（已用「模拟修复前」验证过它确实会失败）。

**实测（修复后）**：网关返回 `HTTP 200 {"reset_users":4,"scope":"all_users"}`。

### 5. 换机时 nginx 起不来：两个片段没有任何安装步骤 🔴

站点模板 include 了两个共享片段，但仓库里只有
`patch-nginx-downloads-redirect.py` 会拷其中一个，另一个**没有任何脚本会拷**。
而 nginx 对 include 一个不存在的文件是 **emerg**（不是 warning）→
`nginx -t` 直接挂 → 站点起不来。严格照 README 部署一台新机器，第 ⑨ 步就死。

**修**：新增 `deploy/install-nginx-assets.sh`（站点 + 片段一次装齐，
装完 `nginx -t` 过了才 reload，失败停原地并留备份；主配置默认不装，
要装得显式 `--main`），README 第 ⑨ 步改用它。

### 6. 注销账号后仍能登进 admin 后台 🔴

wechat 登录和 refresh 都查了 `users.deleted_at`，**只有 admin 登录漏了** ——
注销过的 admin/operator 照样拿密码登进管理后台。三处登录口径必须一致。

**修**：admin 登录补 `deleted_at` 检查。

**实测**（临时软删账号，验证后已清理，残留 0）：
`HTTP 401 {"code":40100,"message":"account has been deleted"}`

## 四、真机验证（小米 Mi 11 / MIUI，Android 11）

改了属主校验之后，App 的三条写路径必须在**真机**上再走一遍 ——
单测证明的是「端点认得」，真机证明的是「App 的流程没被打断」。

真机网络是 172.16.6.0/20 —— 这个网络会 RST 掉到域名的 TLS 连接，
所以整条链路的每一步都自动走了**兜底切 IP**（这恰好是最严苛的环境）。

| 步骤 | 请求 | 结果 |
|---|---|---|
| 登录 | `POST /api/v1/auth/wechat-login` | 域名 Connection reset → 兜底 IP → **200** |
| 剪藏 | `POST /api/v1/articles` | **200**（2079ms，含真实抓取） |
| 列表 | `GET /api/v1/articles` | **200**，文章出现 |
| 蒸馏 | —— | 约 12 分钟后 `ready`，音频 317 秒 |
| 收藏 | `POST /api/v1/articles/{id}/favorites` | 域名 reset → 兜底 IP → **200**；库里 `favorites` id=2 / user_id=22 |
| 稍后听 | `POST /api/v1/articles/{id}/snooze` | **200**；库里 `later_listens` id=3 / user_id=22 |
| 播放 | Media3 拉音频 | 播放中，**0:25 / 5:17** |
| 进度 | `POST /api/v1/articles/{id}/progress` | 每 10 秒一次，全部 **200**；库里 `listening_statuses` id=17 / position_sec=67 |
| 收藏→详情 | `GET /api/v1/articles/{id}` | **200**（不是 403 —— 写进去了就要读得出来） |

最后一条是属主校验这次改动的**核心断言**：收藏写得进去，读也得打得开。
改之前这两个口径是分裂的（写只查存在、读查属主）。

## 五、顺带查出来的性能问题（不在本轮改动范围）

真机等蒸馏时翻到的 worker 日志：

    TTS 响度归一失败：Command '['/usr/bin/ffmpeg', ..., '-af',
    'loudnorm=I=-16.0:TP=-1.5:LRA=11', ...]' timed out after 120 seconds，
    退回原音频

**每个 TTS 分块都要白等 120 秒**才 fallback 到原音频。
`loudnorm` 是两遍分析型滤镜，在这台 2 核机器上跑不完；
一篇文章分十几个块 → 光响度归一就多花好几分钟。

这是「上游 TTS 比健康基线慢约 3 倍」的**具体成因之一**（不是唯一成因）。
可考虑：换更便宜的响度处理（`dynaudnorm` / `volume` + `alimiter`）、
给 ffmpeg 加 `-threads 1` 限制避免超订、或者按音频长度自适应降级。
**本轮没动** —— 它不影响功能闭环，属于独立的性能项。

## 七、本轮**没有**修的（已知、有意留下）

| 项 | 为什么不修 |
|---|---|
| admin 登录无限流 | 公开的 `wechat-login` 有 Redis 限流，admin 登录没有。bcrypt cost 12 把单次尝试拉到 ~200-300ms。**内测阶段规模够用**，上线前必须补（按 email+IP 维度） |
| clawbot 回调不扣配额、不派蒸馏 | mock 性质的端点，与 `submit_article` 口径不一致。要么接上配额，要么从网关暴露面摘掉 |
| 真实 agent 路径退款后没清 Redis「已扣费」标记 | 当下无害（重试不会重复扣），但两套状态长期不一致，后续任何依赖该标记做计费判断的改动都会踩坑 |
| 配额标记 24h TTL → 超时后手动蒸馏会二次扣费 | 需要把扣费事实落库，改动大。要在配额策略定型后一起做 |
| Docker 部署下蒸馏 P95 面板恒为空 | `AI_WORKER_METRICS_URL` 在 compose 里没有、8104 绑在容器回环。当前是 **systemd 部署**，不受影响 |
| admin-web `AdminRole` 里的 `super_admin` / `viewer` 后端不存在 | 前端类型与后端角色集合不一致。后端真实只有 `admin` / `operator` 两档，前端闸门实际形同虚设。收窄类型是**破坏性**改动，等真要分权时一起做 |
| 14 个端点零测试（其中 10 个客户端在调） | 音色 CRUD 与 admin/tags 至少要补「鉴权 + 归属 + 幂等」三层用例。内测阶段先补最热的 |
