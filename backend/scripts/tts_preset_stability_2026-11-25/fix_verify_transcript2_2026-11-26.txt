本期分享的标题是 AI Agent 的架构实战：从玩具到生产的四道坎，内容完整性验证。2025年 AI 智能体项目最常死在哪？不是模型不够聪明，而是系统架构。一份技术报告拆解了 Agent Runtime 四大组件，以及四个最值钱的落地避坑指南。报告的核心观点是：现在智能体项目的上限已经被系统架构卡住，而不是模型参数量。看过演示的人很容易以为模型已经能自己拆任务、调接口、最后整理报告，但真正接近生产环境，第一周往往不是死在模型推理上，而是死在任务拆到一半，状态丢了；工具返回异常，就反复重试；下游智能体把幻觉当事实往下传。所以，智能体项目的瓶颈从模型聪明度转移到了工程架构上。拆开 Agent Runtime，主流框架最后都收敛到四个组件：规划器、记忆仓、工具层、反思器。规划层走循环式决策，模型每次只决定下一步动作，执行完看真实返回值再决定下一步，避免一步失败，后面五步全部作废。max_steps 设置在8到15之间，超了直接转降级流程；工具调用场景，temperature 压到0.1附近；available_tools 也最好由调度层按当前状态过滤，别把几十个工具全丢给模型，否则选工具本身就增加延迟和误用概率。记忆层最容易埋雷，把历史对话全塞进上下文，上下文一长，模型注意力稀释，答非所问。报告给的做法是分三个层：短期上下文只留最近几步；任务记忆管子任务清单；长期记忆用向量库存储，读取时先做权限和时效过滤。两个参数值得记住：摘要触发长度设为上下文60%，到阈值就把更早对话压缩成结构化摘要；向量检索 TopK 设3到5条，太多反而把不相关信息带进来了。记忆写入前做去噪，不是所有观测都值得入库。工具层要当协议来定义，不是本地函数，函数调用出错能回滚，但模型是读自然语言描述后自己挑工具，描述不清就乱调用。报告里给力个典型错误：工具定义只写“根据城市名查天气”，模型经常把它当地理查询工具。所以描述必须写清楚什么情况下用和什么情况下禁用。负向约束比单纯描述功能有效得多。工具返回体要裁剪，单次不超过10KB；超时按接口历史 P95 的3倍设；失败返回结构化错误码，而不是堆栈文本。反思层是智能体和普通 RAG 最大的区别。每执行完一个关键动作，让模型只输出三种判断之一：OK、RETRY、FAST，不给自由发挥空间。反思会额外产生一次模型调用，增加成本和延迟，但能把隐蔽错误早期拦截。实战中不是每个动作都反思，我只对工具调用和最终结果输出做校验，中间状态交给规则引擎，否则成本翻倍。多 Agent 协作不是银弹，带来新的调度复杂度、一致性和调试成本。报告给了一个判断要不要拆的实用信号：单任务步骤超10步，模型开始丢失最初约束；同时涉及多个专业领域，一个 Agent 写代码，又写合规文案，两边都不专业；需要并发读多个外部系统，单 Agent 串行延迟线性叠加，拆成子 Agent 后，总耗时从三者之和变成三者最大值，失败面也被隔离。规划范式演进，编排式先跑通业务，看清楚每个子 Agent 实际输出，再演进到分层或对等式。直接上对等式，往往在排查跨 Agent 问题上花掉比写功能更多的时间。这套架构约束的思路和微服务治理高度吻合。微服务当年也是先自由拆分，后来发现服务间通信、一致性、可观测性才是难点，于是有了服务网格、分布式追踪。智能体现在走的正事这条路，先把组件边界划清楚，再谈协作。报告里的黑板结构共享记忆，本质上是分布式系统里的共享状态加 TTL 加幂等，这跟 Redis 做分布式缓存时的过期策略一脉相承。智能体协作其实是在用分布式系统的老经验解决新问题。状态机外壳之所以有效，是因为它把模型的自由决策装进了确定性的转移表里。这跟传统工作流引擎，比如 Camunda 用 BPMN 约束流程节点是同一套逻辑，但区别在于，工作流引擎的节点是人工定义的，而 Agent 状态机的节点是模型在边界内自己选的，所以它既保留了模型的灵活性，又避免了模型在任意时刻做任意事导致的失控。这意味着确定性兜底和不确定性探索被明确分层了。重试风暴的根子是模型没有“什么时候该放弃”的概念，所以报告给出的方案是结构化错误码加 retryable 字段加失败次数限制，但这里有个更深的判断：只要模型还在自由生成，系统性原因这类推理就永远是模型的能力短板，所以未来的方向不是让模型更聪明地重试，而是从架构上剥夺它重试的权限，系统设计而不是模型能力才是可靠性的来源。记忆污染问题的本质是模型输出最可能回答，而不是验证过的事实。报告用来源校验门来解，但更值得关注的是，当模型输出被当成事实写入长期记忆，错误会自我强化，这意味着长期记忆库的安全审计比短期上下文更重要。未来智能体的记忆治理可能会成为比模型能力更重要的差异化点。多 Agent 协作的上下文一致性问题，本质上跟分布式系统里的一致性协议同构。报告里用黑板结构加 TTL 加密等来解决，但还没提到分布式锁和版本控制，这说明多 Agent 的工程化程度还远没达到分布式系统那套成熟度。未来大概率会引入更严格的版本控制和协调机制。报告最后提到可编程反馈闭环，让 Agent 不只输出动作，还输出自己的验证条件和失败判定标准。这个方向如果走通，意味着智能体从一次性的任务执行器变成能自我修正的系统。但代价是，反馈回路一旦闭环错误，错误会被放大，所以这个方向的真正瓶颈不是模型能力，而是反馈的验证机制。盯住智能体工具层的契约化程度，工具描述里有没有写清什么情况下禁止用？如果大多数团队还停留在只写功能描述，那模型调用不准的抱怨就会一直存在。工具契约的规范可能是下一个工程标准。盯住退化测试的普及，报告里提到的人工制造故障跑100条任务，如果团队不这么做，系统的兜底能力就无从验证。未来，沙箱退化测试可能成为智能体可靠性的标配流程，就像现在的单元测试一样。盯住状态机外壳的落地，如果智能体还是自由发挥，没有状态机约束，那不可控就会一直存在。状态机让系统行为可预期，这是从 Demo 走向生产的关键一步。这份报告的核心是把智能体的可靠性问题从模型能力转移到了工程架构。下次再遇到智能体抽风，先别急着调 prompt，先看它的状态机和轨迹日志。
