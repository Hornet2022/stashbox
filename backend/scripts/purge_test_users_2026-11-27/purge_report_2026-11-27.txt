─── 关键：token 吊销为什么不能漏 ────────────────────────────────────────────

`require_user` **只验 JWT 签名 + 吊销态，不查库**（common/auth.py:125，
注释明说「这一步只多一次 Redis GET，不查库 —— 鉴权在热路径上」）。

⇒ **只删 users 行是不够的**：那些测试账号的旧 access token 在 TTL 内仍然有效，
仍能调接口建新数据（用户行删了，但鉴权不看它）。
⇒ 必须对每个目标用户调 `revocation.revoke(user_id)`，把已签发的 token 全部作废。

端到端验证（造"签发于吊销之前"的真实旧 token，iat_ms 比吊销时刻早 1 小时）：

    uid=12 wx_dev_wechat 测试账号   → HTTP 401 {"message":"Token has been revoked"}
    uid=30 wx_18044444444           → HTTP 401 Token has been revoked
    uid=22 wx_dev_wechat 账号        → HTTP 401 Token has been revoked
    uid=31 smoke probe              → HTTP 401 Token has been revoked
    uid=23 保留：内测用户本人         → HTTP 200（文章列表正常）
    uid=1  保留：Hornet Admin       → HTTP 200

Redis 侧核对：`auth:revoked_after:*` 共 **26** 个键，值形如 `ms:1795763362926`，
与清理时刻吻合（之前用 `redis-cli` 查为 0，是因为 pattern 写错且 redis-cli 的密码
与应用实际使用的不同 —— 核对 Redis 必须用应用自己的连接配置）。

─── 踩坑（留档，防重犯）────────────────────────────────────────────────────

  1. **脚本首版有 bug，第一次执行在"零改动"处中止**：
     `delete(text("表名"))` 在 SQLAlchemy 2.0 会被拒
     （「subject table for an INSERT, UPDATE or DELETE expected, got TextClause」）。
     幸运的是异常发生在任何实际删除之前（第一个目标用户恰好没有文章）⇒
     **DB 零副作用**，事后复查 users 29 / articles 101 / feedback 2328 全部原样。
     ⇒ 修法：用户级关联表一律走**原始 SQL**（表名来自硬编码白名单，无注入面），
     并给每个表的失败加 `rollback` + 记账，最终校验逐表查残留。
     ⇒ 教训：**清理脚本要先 dry-run 跑一遍真实库**，再让删库语句有机会跑。

  2. pg_dump 缺 PGPASSWORD → 「no password supplied」；且 `push_notifications_bak_*`
     对 stashbox 角色无 LOCK 权限 ⇒ 整库 dump 必须 `--exclude-table` 掉它。

  3. 音频文件名带**内容 hash**（`art_xxx.<hash8>.mp3`），按 article_id 打包会
     「Cannot stat」⇒ 必须从 DB 的 audio_url / oss_key 反推真实文件名。
     变体 oss_key 带 `audio/` 前缀，对应根是 `/var/lib/stashbox/data/`（不是 audio 目录）。

  4. 查 Redis 必须用**应用自己的连接配置**（common.redis_client.get_redis_pool），
     `redis-cli -u $REDIS_URL` 的密码与应用实际用的对不上 ⇒ 会误判成"没吊销"。

  5. 验证吊销要用**签发于吊销之前**的 token（iat_ms 更早）；
     刚签发的 token（iat 更晚）本来就不该被吊销判据命中 —— 测错方向会误判成"没生效"。
