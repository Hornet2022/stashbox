# 复盘：内测用户「设置 → 版本」找不到新版本（2026-11-09）

> 一句话：**不是下载坏了，是版本检查压根没让用户下载。**
> 发版手工分三步做，漏了写服务端版本 env 那一步 ⇒ 版本接口仍返回旧号
> ⇒ 安卓客户端判 `latest > installed` 为假 ⇒ 显示「已是最新版本」
> ⇒ **根本没有下载入口**。
>
> 修好线上只花了一步；真正花时间的是**把这个坑变成不可能再犯**。

---

## 1. 用户看到的现象

内测反馈：安卓应用「设置 → 版本」里**找不到新版本**，无法下载。

- 线上当时确实是 0.5.2 的包（已上传、软链已切、下载入口 200 可下载）；
- 但装 0.5.1 的用户打开设置，客户端显示**「已是最新版本」**。

**症状离原因隔了三层**（包在 → 软链对 → 但接口说旧号），
排查时极容易怀疑「下载挂了」「包坏了」「网络问题」「用户手机的问题」——**全都不是**。

---

## 2. 排查路径（都是事实，不是推测）

| 步 | 查了什么 | 结论 |
|---|---|---|
| 1 | 下载地址 `https://stashbox.cn/downloads/latest.apk` | HTTP 200，**字节与本地包逐字节一致** ⇒ 下载链路没问题 |
| 2 | 包内核验（aapt2） | versionCode=25 / versionName=0.5.2 ⇒ 包是对的 |
| 3 | 安卓端 `evaluateUpdate` 判据 | `latest > installed` 才显示下载入口 ⇒ **旧号会被判成"已是最新"** |
| 4 | 版本接口 `/api/v1/app/version` | 返回 `latest_version_code=24` ⇒ **接口说旧号** |
| 5 | 服务端 env | `STASHBOX_APP_LATEST_VERSION_CODE=24` / `NAME=0.5.1` ⇒ **env 漏写** |

⇒ 根因定位：**发版时漏了 env 那一步**，包和软链都到位了，唯独版本接口不知道。

### 为什么漏

发版当时是**手工分三步**做的：`scp` 上传 → `ln -sfn` 软链 → 手改 env。
漏的偏偏是 env 这一步 —— 因为**前三步里前两步有肉眼可见的产物**
（文件在不在、软链指向哪），而 env 改完**页面上看不出任何变化**。

更糟的是：三处各说各的时，**没有任何一处会报错**，页面看起来一切正常。

---

## 3. 修复

- 用**仓内**脚本 `backend/deploy/set_app_version_env.py` 写 env（不是 sed 手改）：
  它会拒绝会静默写坏 systemd `EnvironmentFile` 的值（含换行 / 以 `\` 结尾 / 以引号开头），
  且写前备份、写后回读校验。
  > 实测：第一次跑就被它拦了（更新说明末尾带换行）——
  > **它在写坏之前拒绝，而不是让 user-service 起不来**。
- 重启 `stashbox-user-service` → 版本接口返回 25 / 0.5.2。
- 复核客户端同一判据：versionCode 23/24 ⇒ 「有新版本 0.5.2」可下载；25 ⇒ 「已是最新版本」。

---

## 4. 治本：让它不可能再犯

原来的 `release_apk.sh` **本来就完备**（上传→软链→env→重启→校验→清理），
真正的问题是**不可发现** + **没有独立巡检**。所以这次没有新写第二套发版脚本，
而是把既有脚本变得可发现，并给它配了牙齿。

### 4.1 判定抽成独立模块（判据只有一份实现）

`backend/deploy/release_consistency.py` —— 纯函数、可测，
`check_consistency()` 返回**问题描述列表**而不是 exit code（这样每条判据能单独断言）。
11 条判据：

| # | 判据 | 漏了会怎样 |
|---|---|---|
| 1–3 | env 的 versionCode / 版本名 / 下载地址 == 版本接口说的 | user-service 没重启 ⇒ 接口说旧号 |
| 4 | 版本接口下发的包名 == 软链指向的包名 | 用户点更新拿到跟营销页不一样的包 |
| 5 | 软链指向的文件在磁盘上 | 下载 404 |
| 6 | 软链名里的版本 == env 的版本名 | **本次踩的坑**（包在、软链对、但接口说旧号） |
| 7 | versionCode 是正整数 | 0 ⇒ 客户端判「已是最新版本」 |
| 8–9 | 更新说明 / 发布时间非空 | 更新弹窗显示「服务端未提供更新说明。」 |
| 10–11 | 发布时间 / 更新说明 env == 接口 | **2026-10-25 踩的坑**（0.4.2 的弹窗写着 0.4.1 的说明） |

### 4.2 巡检站在发版流程外面

`backend/deploy/verify_release_consistency.sh` —— **只读、随时可跑**。

为什么要独立：发版脚本只能校验「**自己刚写的东西**」，
它看不见「有人绕过脚本手工发版」与「发完状态又被别的东西动了」。
两者口径不同，不能互相替代 ⇒ `release_apk.sh` 收尾也复用同一份判定。

最后额外查**外网可达性**：状态码 200 **不等于**拿到的是 APK ——
`/downloads/` 路由漏掉时 nginx 的 try_files 会返回 `index.html`，**状态码还是 200**
（这个坑踩过两次）⇒ 所以额外要求 MIME 是 `application/vnd.android.package-archive`。

### 4.3 护栏有牙齿

| 手段 | 数字 | 说明 |
|---|---|---|
| 行为测试 | 27 例 | 每条判据一个用例，且断言**恰好只报这一条** ⇒ 抽掉任一判据，对应用例立刻变红 |
| 变异检验 | **15/15 全部被抓到** | 把实现逐条改坏，必须每条都变红；含「巡检把判定内嵌回 shell」「发版脚本不再复用共享巡检」 |
| 全量回归 | 2129 passed | 无回归；ruff check + format 全绿 |

### 4.4 可发现性（这才是本次真正的病根）

- `backend/deploy/README.md` 新增 **§6.5 安卓内测发版** + **§6.6 独立巡检**；
- `stashbox-android/README.md` 新增「📦 内测发版」章节，**两仓交叉引用**。

之前 `release_apk.sh` 只在 README 里被一句括号提过，而**发版操作者在安卓仓**——
两边没有任何交叉引用 ⇒ 脚本完备但没人知道它存在。
**「不可发现」的完备脚本，等于不存在。**

## 5. 过程中踩到的坑（都是会复发的）

1. **量软链指向文件的大小必须 `stat -L`**（跟随软链）。
   不带 `-L` 时量到的是**链接名本身的长度**（17 字节 = "latest.apk" 这个名字），
   是个会误导排查的**假读数**（看着像"包空了/坏了"）。
2. **测试只 import 调用 ⇒ 抓不到模块级缺陷**。
   实测：`sys` 只在 `main()` 里 import，而模块级是 `sys.exit(main())`
   ⇒ import 路径永不触发 ⇒ 用例全绿；**真跑脚本立刻 NameError**。
   ⇒ 带 `__main__` 入口的工具必须配一条**真跑**用例（subprocess 执行，断言退出码）。
3. **变异锚点会被格式化打断**。ruff format 把长条件拆成多行 ⇒ 锚点"整条条件"失配
   ⇒ 变异检验**假失败**（报"没抓到"其实是"锚点没命中"）。
   ⇒ 锚点用**单行内的短片段**；脚本要能区分"锚点没命中"与"护栏没红"。
4. **env 解析必须按第一个 `=` 切分**（更新说明里就可能有等号），
   且必须**剥掉成对引号**（systemd 读 `KEY="v"` 得到的是 `v`）——
   不剥的话巡检会永远报"不一致"，护栏会被当成噪音关掉。

---

## 6. 可复用的判据（跨项目）

1. 🔴 **"当前版本"这类事实有多处记录时，判定必须独立成可测模块，
   巡检必须独立于生产流程。** 各说各的时**没有任何一处会报错**。
2. 🔴 **每条判据要能被单独测出来**：构造"只违反这一条"的数据 ⇒ 断言**恰好**产出 1 条问题。
   只断言"报不报错"的测试等于没写。
3. 🔴 **工具脚本的测试必须真跑**（subprocess），否则模块级缺陷永远测不到。
4. 🔴 **状态码 200 ≠ 拿到的是目标文件** ⇒ 校验 MIME。
5. ⚠️ **"完备但不可发现"的脚本等于不存在** ⇒ 写完脚本先问"操作者在哪个仓？他知道吗？"

---

## 7. 现状与残留

- 线上：0.5.2 / versionCode 25，env、软链、磁盘文件、版本接口**四处一致**；
  内测用户已确认能从「设置 → 版本」看到并下载新版本。
- 巡检可随时跑：`bash backend/deploy/verify_release_consistency.sh`（只读）。
- **APK 保持单一分发渠道**（`stashbox.cn/downloads`）——
  不引入 GitHub Release，避免用户拿到两个版本来源导致版本混淆。
- 客户端侧仍有已知兜底：部分国产 ROM 会拦截 App 下载自身 APK，
  此时走浏览器兜底分支（本轮未触发）。
