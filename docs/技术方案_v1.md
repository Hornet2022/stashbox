### §0a.5 常见问题 FAQ（v1.2 r11 增量 · 2026-09-09 24:15 承宇自主推进）

> **为什么这节**：开发读 v1 时，会遇到很多"为什么用 X 不用 Y"的问题——FAQ 把这些问题的答案集中到头部，避免每个开发都去翻全文。

**Q1：为什么不用 Go 写后端？**
- A：LLM SDK（Claude / Qwen / 豆包）Python 生态最佳；FastAPI 异步性能足够；Python 招人比 Go 容易（一期 5.5 人）。二期若 ai-service 性能瓶颈再加 Go 服务。

**Q2：为什么不用 MongoDB？**
- A：PostgreSQL 14 JSON 字段强 + LATERAL JOIN（蒸馏 Step 关联查询）；14 张表里有 5 张是关系型（用户/订阅/支付/标签/任务），不适合文档型。

**Q3：为什么 v1 里有产品内容（如 §0a）？**
- A：§0a 是**技术视角的快速导航**（章节速览 +必读 + SOP 索引），不是产品定位。真正的产品定位在 v2 §0+§1，**v1 不复刻**（详见 §0a.3 与 v2 的关系）。

**Q4：为什么 4 服务而不是 6 服务？**
- A：6 服务过细（每个服务都有 K8s manifest + 数据库 + 监控），一期 5.5 人维护成本高；4 服务平衡扩展性（user/content/ai/collector）+ 维护成本。

**Q5：为什么 §3.0 写 JWT 7天过期但 §10.9 写 refresh 7天？**
- A：§3.0 是 API 鉴权（access 7 天）；§10.9 是安全策略（refresh token 30 天轮转）——两个不同维度的描述。详见 §3.0 vs §10.9 决策记录。

**Q6：为什么不用 Kong / APISIX 做 API Gateway？**
- A：自研 Nginx 路由简单可控，国内合规要求（Kong 部分模块需要商业 license）；二期流量大了可换 Kong。

**Q7：为什么 §2.3 L4 蒸馏只写 3 行 "详见 §5"？**
- A：v1.2 r10 已修订——现在 §2.3.1-§2.3.4 详细写"5 子模块 + 依赖 + API 数量 + 部署形态"。原版是 v1 早期版本没细化。

**Q8：为什么 L4 蒸馏不用专门的蒸馏服务（如开源项目）？**
- A：听匣的 L4 是"4 步流水线"（Step 1 多模态 → Step 2 听感改写 → Step 3 主题标签 → Step 4 TTS），每个 Step 用不同模型（Qwen VL / Claude / 豆包），**不是单一蒸馏模型**。开源蒸馏项目（如 Hugging Face 的 distill-whisper）只覆盖单一场景。

**Q9：为什么 v1 章节序号有 §0a/§0b/§0c 在 §1 之前？**
- A：v1 §0a/b/c 是**技术视角的导航入口**（按"先看哪几章"组织），不参与 §1-§11 的技术章节编号。读 v1 时，先看 §0a 找必读章节，再深入 §1-§11。

**Q10：为什么 v1 提到"详见 §5"很多次？**
- A：v1 §2/§3/§10 都涉及"蒸馏"概念，§5 是蒸馏引擎的完整描述。读 v1 时，遇到"详见 §5"先跳 §5 蒸馏，再回到原章节。

**依赖关系矩阵**：
| 调用方 → 被调方 | User Service | Content Service | AI Service | Redis | OSS |
|---|---|---|---|---|---|
| **API Gateway** | ✅ 直调 | ✅ 直调 | ✅ 直调 | - | - |
| **User Service** | - | ❌ 不调 | ❌ 不调 | ✅ 配额缓存 | ❌ |
| **Content Service** | ✅ 鉴权调用 | - | ✅ 触发蒸馏 | ✅ 抓取缓存 | ✅ 上传音频 |
| **AI Service** | ❌ 不调 | ✅ 拉原文 | - | ✅ 蒸馏队列 | ❌ |
| **抓取 Worker**（海外） | ❌ 不调 | ✅ 拉取队列 | ❌ | ✅ 队列 | ❌ |

**关键约束**：
- **User Service 不调 Content / AI**——避免鉴权链路依赖业务
- **AI Service 不调 User Service**——避免蒸馏链路鉴权
- **抓取 Worker 海外 ECS**——只调 Content Service 拉取队列，不调其他
- **OSS 只被 Content Service 写**——其他服务只读不写

**调用方式**：
- **同步调用**（REST + 内网 mTLS）：Content → AI 触发蒸馏
- **异步调用**（Redis 队列 + Worker 拉取）：抓取 / 蒸馏
- **WebSocket 推送**（蒸馏完成 → App）：AI → API Gateway → Client

## §2 模块拆分（4 服务 + 6 职责层）

> **二维结构**：本章按"职责层"切（收集/抓取/L4蒸馏/业务/用户/监控 6 层），实际部署对应 4 个微服务（api-gateway/user/content/ai）+ 1 个 worker 进程（fetch worker）。
> - §2.1 + §2.2（收集 + 抓取）= content-service 内的两个子层
> - §2.3（L4 蒸馏）= ai-service（独立部署）
> - §2.4（业务）= content-service（共享 + 扩展）
> - §2.5（用户）= user-service（独立部署）
> - §2.6（监控）= 4 个服务共享 Prometheus 客户端

### 2.1 收集层（Content Collector，content-service 子层）

**职责**：从 5 条入口接收 URL/文件，调度抓取 + 蒸馏

| 组件 | 技术 | 说明 |

### 2.2 抓取层（Fetch Worker）

#### 2.3.1 蒸馏引擎模块结构（v1.2 r10 增量 · 2026-09-09 24:05 承宇自主推进）

> **为什么这节**：v1 §2.3 之前只有 3 行 "详见 §5"——开发不知道蒸馏引擎由哪些子模块组成。

**5 个子模块**：

| 子模块 | 职责 | 实现 | 详见 |
|---|---|---|---|
| **结构化提取器** | Step 1：图文/视频 → 结构化 JSON | Qwen2.5-VL-72B | §5.2 |
| **听感改写器** | Step 2：结构化 JSON → 听感稿 Markdown | Claude 4 Sonnet | §5.3 |

| **失败处理器** | 降级路径（fallback_raw_tts）| 原文 → TTS 直读 | §5.6 |

**Worker 模型**：
- **DistillWorkerPool**：5 个并发 Worker（部署在 cn-hangzhou 4C8G × 2）
- **队列**：Redis List `distill_queue`（FIFO）
- **状态**：distill_tasks 表 status 字段（pending / running / done / failed）

## §3 API 契约

### 3.0 整体框架

**API 分层（4 层）**：

| 层 | 职责 | 协议 | 示例 |
|---|---|---|---|
| **L1 用户端 API** | App / 浏览器扩展主动调用 | REST + JWT | `/api/v1/articles/add` |
| **L2 回调 API** | 微信 / Apple / 支付回调 | REST POST + 签名 | `/api/v1/callback/wechat` |
| **L3 实时推送** | 蒸馏进度 / 通知 / 后台播放状态 | WebSocket | `/ws/articles/{id}/progress` |
| **L4 内部 RPC** | 微服务之间调用（暂用 REST，未来可换 gRPC）| REST + 内网 mTLS | `content-service/articles/parse` |

**基础 URL**：`https://api.stashbox.cn/v1`

**认证**：
- **L1 用户端** → `Authorization: Bearer <jwt>`（HS256 签名，access token 7 天过期，refresh token 30 天过期，详见 §3.0 鉴权 + §10.9 安全策略）
- **L2 回调** → 微信 XML 签名 / Apple JWS / 支付 HMAC-SHA256
- **L3 WebSocket** → URL query 携带 JWT（`?token=<jwt>`）
- **L4 内部** → mTLS 证书 + Service Token

**统一响应格式**：
```json
{
  "code": 0,
  "message": "ok",
  "data": {...},
  "trace_id": "tr_xxx",
  "server_ts": 1725859200
}
```

**错误码体系（按模块分组）**：

| 范围 | 模块 | 含义 | 示例 |
|---|---|---|---|
| `0` | 通用 | 成功 | - |
| `1000-1099` | 鉴权 | 登录态/权限 | `1001` JWT 过期 / `1002` refresh_token 失效 |
| `2000-2099` | 文章 | 加入/查询/状态 | `2001` URL 不支持 / `2002` 抓取失败 / `2003` 蒸馏超时 |
| `3000-3099` | 配额 | 用量扣减 | `3001` 月配额用尽 / `3002` 文章超长 |
| `4000-4099` | 订阅 | 会员/支付 | `4001` 支付校验失败 / `4002` 订阅已过期 |
| `5000-5099` | 系统 | 限流/上游 | `5001` 频率超限 / `5002` LLM 上游超时 / `5003` TTS 上游 5xx |
| `9xxx` | 服务 | 内部故障 | `9001` DB 连接失败 / `9002` 队列堆积 |

**频率限制（按用户 / 按 IP 双重）**：

| API | 用户级 | IP 级 | 说明 |
|---|---|---|---|
| 加入文章 | 30/分钟 | 60/分钟 | 防爬 + 防误触 |
| 待听列表 | 60/分钟 | 120/分钟 | - |
| 其他读 API | 120/分钟 | 240/分钟 | - |
| 登录 | 10/分钟 | 30/分钟 | 防撞库 |
| 蒸馏进度 WS | - | 100/分钟 | 每个连接独立计数 |
| 回调 | - | 1000/分钟 | 微信支付回调限速 |

**幂等性设计**：
- `POST /articles/add` 接受 `client_request_id`（UUID），重复请求返回相同 article_id
- `POST /articles/{id}/mark-listened` 用 `(user_id, article_id, action)` 做幂等键
- 支付回调用微信 transaction_id 做幂等键（数据库唯一索引兜底）

### 3.1 内容域（Articles）

#### POST `/api/v1/articles/add`（加入文章）

**用户故事**：用户在微信/抖音/任意网页/App 主动触发加入

**请求**：
```json
{
  "url": "https://mp.weixin.qq.com/s/xxx",
  "source": "wechat|douyin|web|pdf|word",
  "title": "可选，预填",
  "client_request_id": "uuid-v4"
}
```

**响应**：
```json
{
  "article_id": "art_xxx",
  "status": "queued",
  "estimated_distill_seconds": 30,
  "estimated_listen_minutes": 28,
  "quota_remaining": 27
}
```

**错误场景**：
- `2001` URL scheme 不支持（仅 http/https）
- `2002` 抓取失败（404/超时/反爬）→ 客户端提示"内容不可达，换个链接试试"
- `3001` 月配额用尽 → 客户端展示付费墙

**配额扣减**：响应返回前**同步完成**（事务，乐观锁），失败回滚

#### GET `/api/v1/articles/pending`（待听列表）

**分页策略**：游标分页（按 `distilled_at DESC + id DESC` 复合游标，避免深分页性能问题）

**请求**：`?cursor=eyJ0IjoxNzI1ODU5MjAwLCJpIjoiYXJ0X3h4eCJ9&size=20`

**响应**：
```json
{
  "articles": [
    {
      "id": "art_xxx",
      "title": "...",
      "word_count": 8000,
      "image_count": 5,
      "distilled_at": "2026-09-08T10:00:00Z",
      "listen_minutes": 28,
      "tags": ["AI", "..."],
      "source": "wechat",
      "audio_url": "https://cdn.stashbox.cn/audio/xxx.mp3",
      "audio_signed_url_expires_at": "2026-09-08T11:00:00Z"
    }
  ],
  "next_cursor": "...",
  "has_more": true
}
```

**音频 URL 签名**：CDN 用 OSS 签名 URL，**1 小时过期**，过期时 App 端自动重新拉

#### GET `/api/v1/articles/listened`（听过列表）

**过滤参数**：`?from=2026-08-01&to=2026-08-31&tag=AI`

**响应结构同 pending**，但状态字段为 `listened`

#### POST `/api/v1/articles/{id}/mark-listened`

**幂等键**：`(user_id, article_id, "mark-listened")`

**请求体**：可携带 `listened_seconds`（用于断点续听场景）

**副作用**：
- 更新 `listening_status.status = listened` + `listened_at`
- 写 `feedback` 表（type = listen_complete）
- **不**触发配额退还（已消耗的不会退）

#### POST `/api/v1/articles/{id}/skip`

**请求体**：`{ "reason": "too_long|boring|low_quality|other", "metadata": {} }`

**副作用**：写 `feedback` 表（type = skip）→ 用于未来推荐算法

#### POST `/api/v1/articles/{id}/favorite`

**幂等键**：`(user_id, article_id, "favorite")`

**副作用**：在 `articles.metadata` 加 `favorited_at` 字段（避免新表）

#### GET `/api/v1/articles/{id}`（文章详情）

**返回**：原文 + 蒸馏稿 + 音频 URL + 图表列表 + 标签

**用途**：App 详情页 + 调试页 + 后续导出 PDF

#### 管理后台设计 5 原则
- **所有写操作必填 `reason` 字段**——事后审计
- **管理员操作**走独立 `admin_operation_logs` 表（与用户 `operation_logs` 物理隔离）
- **敏感操作二次确认**（如删除用户、改配额扣减方向）
- **admin JWT** 有效期 2 小时（比普通用户短），refresh 需重新登录
- **所有管理 API 走独立限流**（30/分钟，防爆破）

**配额扣减（核心事务）**：

```sql
-- 伪代码：原子扣减，失败回滚
BEGIN;
  -- 1. 锁定配额行
  SELECT quota_used, quota_total FROM user_quotas
    WHERE user_id = $1 AND month = $2
    FOR UPDATE;

  -- 2. 检查余额
  IF quota_used >= quota_total THEN
    ROLLBACK;
    RETURN 3001;  -- 配额用尽
  END IF;

  -- 3. 扣减（带 WHERE 防超扣）
  UPDATE user_quotas
    SET quota_used = quota_used + 1, updated_at = NOW()
    WHERE user_id = $1 AND month = $2 AND quota_used < quota_total
    RETURNING quota_used;

  -- 4. 如果返回 0 行，说明超扣（并发情况）
  IF NOT FOUND THEN
    ROLLBACK;
    RETURN 3001;
  END IF;
COMMIT;
```

**月度重置**：定时任务每月1号 00:00 创建新 month 行（不删旧数据，留作历史）

async def process_task(task):
    try:
        result = await run_distill(task.article_id)
        task.status = 'done'
        task.finished_at = now()
    except LLMError as e:
        task.retry_count += 1
        if task.retry_count >= task.max_retries:
            task.status = 'failed'
            task.error_code = e.code
            # 通知用户 + 退还配额
            await notify_user(task.user_id, "蒸馏失败")
            await refund_quota(task.user_id)
        else:
            task.status = 'pending'  # 重新入队
            await sleep(2 ** task.retry_count)  # 指数退避
    except PermanentError as e:  # 抓取失败等不可恢复错误
        task.status = 'failed'
        task.error_code = e.code
        await refund_quota(task.user_id)

### 4.10 配额扣减事务（v1.2 新增 · Hornet 2026-09-09 拍板）

#### 4.10.1 设计目标
- **强一致**：扣减失败必须回滚，不能让用户白嫖
- **高性能**：单 API 调用 < 50ms（含事务）
- **可恢复**：崩溃后配额不丢（事务提交才生效）
- **可观测**：每次扣减写 `operation_logs`（合规留存）

#### 4.10.2 乐观锁方案（PostgreSQL）

**核心字段**：`user_quotas.version BIGINT DEFAULT 0`（每次 UPDATE 自增）

**事务 SQL 模板**：
```sql
BEGIN;

-- Step A：读当前版本 + 校验
SELECT quota_total, quota_used, version
INTO @total, @used, @version
FROM user_quotas
WHERE user_id = $1 AND month = $2
FOR UPDATE;  -- 行级锁，防并发

-- Step B：业务校验
IF @total = -1 OR @used < @total THEN
  -- 配额足够 / 无限配额
  UPDATE user_quotas
  SET quota_used = quota_used + 1, version = version + 1, updated_at = NOW()
  WHERE user_id = $1 AND month = $2 AND version = @version;
  
  GET DIAGNOSTICS row_count = ROW_COUNT;
  
  IF row_count = 0 THEN
    -- 版本冲突，抛错让上层重试
    ROLLBACK;
    RAISE EXCEPTION 'quota_version_conflict_retry';
  END IF;
  
  -- 写审计日志
  INSERT INTO operation_logs(user_id, action, delta, reason, trace_id)
  VALUES ($1, 'quota_deduct', 1, $3, $4);
ELSE
  ROLLBACK;
  RAISE EXCEPTION 'quota_exhausted' USING ERRCODE = '3001';
END IF;

COMMIT;
```

**关键点**：
- `FOR UPDATE` 行锁——同用户并发请求串行化
- `version` 乐观锁——防锁等待期间被其他事务改
- `GET DIAGNOSTICS` 检查 affected rows——版本冲突自动回滚
- `RAISE EXCEPTION USING ERRCODE` —— 直接映射错误码（前端 `3001` 月配额用尽）

#### 4.10.3 重试策略（应用层）

**指数退避 + 抖动**：
- 第1次重试：50ms ± 10ms 随机
- 第2次重试：100ms ± 20ms
- 第3次重试：200ms ± 40ms
- 最多 3 次 → 给前端返回 `5001 频率超限`（让用户重试按钮）

**重试条件**：仅 `quota_version_conflict_retry` 错误码重试；其他错误不重试

#### 4.10.4 配额退还（蒸馏失败场景）

**触发**：
- ai-service Worker 标记 `distill_tasks.status = failed`
- content-service 监听 task 失败事件 → 调用 `POST /admin/users/{id}/quota-adjust`（admin API 退还）
- 或在 `articles.status = failed` 时**自动退还**（无须 admin 介入）

**事务 SQL**（与扣减镜像，但 delta = -1）：
```sql
UPDATE user_quotas
SET quota_used = GREATEST(0, quota_used - 1), version = version + 1
WHERE user_id = $1 AND month = $2;
```

#### 4.10.5 配额计费窗口

**月度窗口**：`month` 字段 = `'2026-09'`（YYYY-MM 格式），每月 1 号 00:00 自动开新窗口

**跨月处理**：
- 9 月 30 日加的 quota_total = 50，配额没用完
- 10 月 1 日 00:00 → 新窗口 `month='2026-10'`，quota_total 重置为 50
- 9 月的 quota_used 保留（统计用），但不限制 10 月用量

**回填机制**：用户月初首次访问 → 触发 `INSERT ... ON CONFLICT DO NOTHING` 创建当月 `user_quotas` 行

| 指标 | 阈值 | 告警 |
|---|---|---|

| 版本冲突率（%）| < 1% | > 5% 说明热点用户，加锁优化 |

## §5 L4 蒸馏引擎设计

### 5.0 整体框架

**目标**：把任意来源的"长篇图文 / 视频" → "通勤场景下 5-30 分钟听感音频"

**核心约束（5 条铁律）**：

| # | 铁律 | 量化指标 |
|---|---|---|
| 1 | **信息密度调控** | 200-260 字/分钟（实测通勤最佳） |
| 2 | **数字听感化** | 百分号 → 念出；年份 → 默认不念 |
| 3 | **图表叙事化** | 每张图 1-3 句口语描述，不超过 3 句 |
| 4 | **段落口语化** | 删"综上所述"、"值得注意的是"等书面连接词 |
| 5 | **错误率控制** | TTS 不读错字、不读破句 |

**引擎组成（4 步流水线）**：

```
Step 1 (多模态理解)  → Step 2 (听感改写)  → Step 3 (主题标签)  → Step 4 (TTS 合成)
     ↓                     ↓                    ↓                    ↓
  Qwen2.5-VL-72B      Claude 4 Sonnet      Claude 4 Sonnet       豆包 TTS
     ↓                     ↓                    ↓                    ↓
  结构化摘要 JSON      听感稿 Markdown      3-5 个标签            MP3 + 文字稿
```

**Worker 模型**：
- 单篇文章 1 个 Worker 全流程跑完（避免跨 Worker 状态同步）
- 队列优先级：`priority=1`（用户升级）> `priority=5`（默认）> `priority=10`（批量灌入）
- 并发数：默认 5 个 Worker，可动态调整

### 5.6 端到端失败处理

#### 失败分类

| 错误码 | 含义 | 重试策略 | 用户通知 |
|---|---|---|---|
| `2001` | URL scheme 不支持 | 不重试 | 立即返回 2001 |
| `2002` | 抓取失败（404/超时/反爬）| 重试 3 次 | 退还配额 + 提示"内容不可达" |
| `5002` | Step 1 LLM 失败 | 切 Claude fallback | 退还配额 + 提示"稍后重试" |
| `5003` | Step 2 Claude 失败 | 重试 3 次 | 退还配额 + 提示"稍后重试" |
| `5004` | Step 4 TTS 失败 | 切 CosyVoice fallback | 退还配额 + 提示"稍后重试" |
| `9001` | DB 故障 | 重试 3 次 | 系统告警 + 退还配额 |

#### 降级路径（特殊）

**Step 1 + Step 2 都失败** → 走"原文朗读"降级路径：
```
抓取成功 + LLM 全失败 → 直接用原文 → TTS（不加听感改写）
```

**优点**：用户至少能听个响；**缺点**：听感差，需要在客户端标记"原文版"

#### 重试 + 退避

```python
async def distill_with_retry(article_id, max_retries=3):
    for attempt in range(max_retries):
        try:
            result = await run_full_pipeline(article_id)
            return result
        except (LLMError, TTSError) as e:
            if attempt < max_retries - 1:
                await asyncio.sleep(2 ** attempt)  # 1s, 2s, 4s
                if attempt == 1 and isinstance(e, LLMError):
                    # 第二次失败时切换 fallback
                    switch_to_fallback_model()
            else:
                # 3 次都失败，走降级路径
                return await fallback_raw_tts(article_id)
        except PermanentError as e:
            # 抓取失败不可恢复
            await refund_quota(article_id.user_id)
            raise HTTPError(2002, "内容不可达")
```

| **prompt 模板** | Step 2 听感改写 prompt v2 vs v1 | 5% v2 / 95% v1 |
| **模型选型** | Step 2 改用 Claude 3.7 vs Claude 4 Sonnet | 10% 3.7 / 90% 4 |
| **TTS 音色** | 豆包 4 种音色 × 性别 × 语速 | 25% × 4 组 |
| **蒸馏步骤** | 4 步 vs 5 步（新增"摘要标题生成"）| 50% × 2 组 |

#### 5.8.3 实现机制：基于 `app_configs` 表 + 流量分桶

**新增字段**：`app_configs.value` 存实验配置 JSON：
```json
{
  "experiment_id": "exp_2026_09_distill_v2",
  "enabled": true,
  "traffic_percent": 5,
  "variant": "v2",
  "user_segment": "all | new_user | member | power_user",
  "start_at": "2026-09-15T00:00:00Z",
  "end_at": "2026-09-30T23:59:59Z",
  "success_criteria": {
    "min_sample_size": 1000,
    "target_metric": "listened_30s_rate",
    "min_lift": 0.02
  },
  "fallback_config_key": "distill_prompt_v1"
}
```

**流量分桶（一致性 hash）**：
```python
def get_distill_variant(user_id, article_id, experiment_config):
    if not experiment_config['enabled']:
        return experiment_config['fallback_config_key']
    
    # 用 user_id + article_id 做 hash，保证同篇文章同一实验只走一个桶
    hash_input = f"{user_id}:{article_id}:{experiment_config['experiment_id']}"
    bucket = int(hashlib.md5(hash_input.encode()).hexdigest(), 16) % 100
    
    if bucket < experiment_config['traffic_percent']:
        return experiment_config['variant']
    else:
        return experiment_config['fallback_config_key']
```

**关键点**：**user_id + article_id 哈希**保证：
- 同篇文章全文 4 步走同一变体（不出现"前半篇 v1 后半篇 v2"）
- 不同用户分桶稳定（同一用户实验期间都在同一组）

#### 5.8.4 监控指标（每变体独立采集）

| 指标 | 计算 | 目标 |
|---|---|---|
| **listened_30s_rate** | 听完 30 秒的用户 / 加入用户 | 越高越好（听感好）|
| **complete_rate** | 听完 / 加入 | 越高越好（内容完整） |
| **skip_rate_30s** | 30 秒内跳过的 / 加入 | 越低越好（开头听感差）|
| **average_listen_seconds** | 平均收听时长 | 越长越好 |
| **cost_per_article** | 单篇蒸馏成本 | 越低越好 |
| **distill_success_rate** | 蒸馏成功率 | 越高越好 |
| **rerun_rate** | 重新蒸馏率（用户主动重听）| 越高越好（主动重听 = 内容好） |

**核心指标**：`listened_30s_rate`（30 秒留存率 = 听感的第一道关，过了这道关大概率会听完）

#### 5.8.5 显著性检验 + 自动决策

**统计引擎**：每 4 小时跑一次显著性检验
```python
from scipy.stats import proportion_ztest

control_conversions = 850  # v1 听完 30s
control_total = 1000
treatment_conversions = 920  # v2 听完 30s
treatment_total = 1000

z_stat, p_value = proportion_ztest(
    [control_conversions, treatment_conversions],
    [control_total, treatment_total]
)

if p_value < 0.05 and (treatment_conversions/treatment_total) > (control_conversions/control_total) + 0.02:
    # p < 0.05 显著 + 提升 ≥ 2%，通过
    return "promote"
elif p_value < 0.05 and (treatment_conversions/treatment_total) < (control_conversions/control_total):
    # 显著负向，回滚
    return "rollback"
else:
    # 不显著，继续观察
    return "continue"
```

#### §A.6 月度 Token 预算（v1.2 新增 · Hornet 2026-09-09 拍板）

**§A.4 算的是单篇成本，但没人算过"一个月到底要花多少钱"**——这是产品评审必须有的数字。

**用户量级 × 月配额 × 单篇成本 = 月度总成本**：

| 用户量级 | 月配额 | 平均活跃度 | 月蒸馏篇数 | 单篇成本 | 月度总成本 |
|---|---|---|---|---|---|
| 100 内测用户 | 50 篇 | 30%（CP7 实测）| 1,500 篇 | ¥1.43 | **¥2,145** |
| 1,000 早期付费 | 50 篇 | 40% | 20,000 篇 | ¥1.43 | **¥28,600** |
| 10,000 A 轮 | 50 篇 + D 类 100 篇 | 50% | 275,000 篇 | ¥1.43（混合 ¥1.82）| **¥420,000** |
| 50,000 B 轮 | 同上 | 60% | 1,650,000 篇 | ¥1.43（混合 ¥1.82）| **¥2,520,000** |

**关键观察**：
- **100 内测期 ¥2,145/月**：完全可承担（公众号文章蒸馏一年也就 ¥26k）
- **1k 用户 ¥28,600/月**：月收入按 8% 付费率 × ¥39 = ¥3,120——**亏损 9 倍**（这正是一期"内测亏损常态"的本质）
- **10k 用户 ¥420,000/月**：必须把单篇成本压到 ¥0.50 以下，否则盈不了利
- **降本路径**：
  - Step 2 Claude 4 → Claude 3.7（成本降 40%）
  - TTS 豆包 → 阿里 CosyVoice（成本降 30%）
  - 内容去重（同一文章只蒸馏一次，缓存命中 20%+）

### 6.3 主备切换链路（降级策略）

```
正常路径（80% 流量）
豆包语音 → MP3 → OSS
   ↓ 豆包 5xx / 超时（> 3 秒）
   ↓ 自动 fallback
CosyVoice → MP3 → OSS
   ↓ CosyVoice 也挂
   ↓ 二次 fallback
阿里云 TTS → MP3 → OSS
   ↓ 全挂
   ↓ 标记 error_code=5004 + 退还配额
用户 App 提示"暂时无法合成，请稍后重试"
```

**实现细节**：
- **超时**：单 TTS 调用 > 3 秒触发切换（避免用户等待焦虑）
- **重试**：主备各重试 1 次（避免抖动误切）
- **熔断**：连续 50 次失败熔断 5 分钟（保护上游）
- **降级路径**（终极 fallback）：TTS 全挂 → 走 Step 2 的听感稿文本 + 系统自带的本地 TTS（基础质量，保证至少能响）

### 6.4 主观评测方法（每季度盲测）

**目的**：验证豆包音质是否真的"自然"，避免凭感觉选错 TTS

**评测流程**（每季度 + 重大 prompt 切换时）：
1. **采样**：抽 10 篇文章 × 4 种 TTS（豆包/CosyVoice/阿里/腾讯）= 40 段音频
2. **盲测**：5 名内部测试员（不含作者）打分（1-5 分 MOS 评分）
3. **维度**：
   - 听感自然度（5 分制）
   - 数字读法准确率（"32%" → 念"百分之三十二"）
   - 多音字准确率（"行长" vs "行业"）
   - 断句自然度（长句切分位置）
4. **数据沉淀**：评测结果写 `tts_evaluation_logs` 表，跟踪每季度趋势

**告警**：任一维度 MOS < 3.5 → 触发 TTS 切换评估

### 6.6 听匣自带的"通勤场景优化"

针对地铁噪声场景，对 TTS 输出做后处理：
- **语速微调**：默认 1.0×，可调 0.8× / 1.2× / 1.5× / 2.0×
- **加重关键数字**："百分之三十二" → "百分之三十二"（重读"三十"）+ 停顿 0.3 秒
- **段落停顿**：Markdown 的 `##` 段落 → TTS 输出加 0.8 秒停顿
- **数字强制听感化**（后处理在文本预处理阶段）：
  - "32%" → "百分之三十二"
  - "¥29" → "二十九元"
  - "2026 年" → "二零二六年"（年份不读"两千零二十六"）
  - "10k" → "一万"
- **缩写展开**：API → A-P-I / AI → A-I / LLM → L-L-M（避免 TTS 念错）

**后处理层位置**：在 ai-service Worker 内，Step 4（TTS 调用前）插入 `text_normalizer.py` 模块

#### 6.7.1 监控实现（v1.2 增量 · 2026-09-09 23:45 承宇自主推进）

**Prometheus 指标定义**：
```python
from prometheus_client import Counter, Histogram

TTS_CALLS = Counter(
    'tts_calls_total',
    'Total TTS calls',
    ['engine', 'voice', 'status']  # status = success / failure
)

TTS_DURATION = Histogram(
    'tts_duration_seconds',
    'TTS synthesis duration',
    ['engine', 'voice'],
    buckets=[0.5, 1, 2, 3, 5, 10]
)

TTS_COST = Counter(
    'tts_cost_cents_total',
    'TTS cost (cents)',
    ['engine', 'voice']
)
```

**采样点**：
- **每个 TTS 调用前**：`TTS_CALLS.labels(engine=..., voice=..., status='pending').)`
- **调用成功**：`TTS_CALLS.labels(status='success').)` + `TTS_DURATION.observe(duration)`
- **调用失败**：`TTS_CALLS.labels(status='failure').)` + 错误码 label

**告警规则**（PromQL）：
```yaml
- alert: TTSFailureRateHigh
  expr: |
    sum(rate(tts_calls_total{status="failure"}[5m])) by (engine)
    / sum(rate(tts_calls_total[5m])) by (engine)
    > 0.10
  for: 5m
  annotations:
    summary: "TTS 失败率 > 10%（{{ $labels.engine }}）"
    action: "检查 TTS 引擎状态 + 触发主备切换"

- alert: TTSDurationP95High
  expr: |
    histogram_quantile(0.95, 
      sum(rate(tts_duration_seconds_bucket[5m])) by (le, engine, voice)
    ) > 5
  for: 10m
  annotations:
    summary: "TTS P95 > 5 秒（{{ $labels.engine }}/{{ $labels.voice }}）"

- alert: TTSFallbackRateHigh
  expr: |
    sum(rate(tts_calls_total{status="failure", fallback_used="true"}[5m]))
    / sum(rate(tts_calls_total[5m])) > 0.05
  for: 10m
  annotations:
    summary: "TTS fallback 触发率 > 5%"
    action: "检查主引擎状态 + 评估切换"
```

### 7.4 CDN 配置（v1.2 增量 · 2026-09-09 23:45 承宇自主推进）

**为什么需要 CDN**：
- 音频文件平均 5 MB（30 分钟听感稿 m4a 128kbps），OSS 直出带宽成本高
- CDN 边缘节点分发，用户就近读取（首屏 < 200ms）
- 减少 OSS 流量计费（CDN 回源流量 ≈ 1/10 直出）

**阿里云 CDN 配置**：
```
源站类型：OSS 域名
源站地址：tingxia-audio-prod.oss-cn-hangzhou.aliyuncs.com
加速域名：audio.stashbox.cn（音频专用）
缓存策略：
  - .m4a / .mp3：缓存 30 天（HTTP 200 + Cache-Control: max-age=2592000）
  - .json / .png：缓存 7 天
  - 其他：缓存 1 天
回源 HOST：tingxia-audio-prod.oss-cn-hangzhou.aliyuncs.com
HTTPS：开启（Let's Encrypt 通配符证书 *.stashbox.cn）
HSTS：开启（max-age=31536000; includeSubDomains; preload）
Range 回源：开启（音频分片播放）
```

**缓存刷新策略**：
- 音频文件：生成后 30 天不刷新（URL 带 hash 参数，强制回源）
- 图片：手动刷新（运营后台有"刷新 CDN"按钮）

**回源带宽成本**：
- 1 万用户 × 30 篇/月 × 5 MB = **1.5 TB/月**
- CDN 价格 ¥0.18/GB → ¥270/月
- OSS 回源 ¥0.15/GB → ¥225/月
- 总计 **¥495/月**（vs 直出 ¥2700/月）

**加速效果**：
- 首屏延迟：OSS 直出 800ms → CDN **150ms**
- 断流率：直出 3% → CDN **0.5%**（节点切换快）

### 8.1 D9 5 大失败场景（v1.2 新增）

| # | 场景 | 触发条件 | 严重度 | 兜底路径 |
|---|---|---|---|---|
| **F1** | **Universal Links 不生效**（iOS 9+）| 用户没装 App 时点链接 → 应跳转应用商店但跳浏览器 | 高 | URL Scheme fallback |
| **F2** | **App Links 验证失败**（Android）| SHA256 指纹不匹配 / assetlinks.json 缺失 | 高 | 普通 Deep Link |

### 8.2 5 场景的详细降级路径

#### F1: Universal Links 不生效
**触发**：用户没装 App 时 iOS 跳浏览器（应用商店）而不是 App Store

**降级**：
1. 浏览器打开 → 我们的 H5 引导页
2. H5 页引导 → "下载听匣 App"，自动跳转应用商店
3. 用户下载 App → 首次启动时 H5 引导页带的 `pending_url` 自动恢复任务
4. 任务成功加入听匣

**关键代码**（前端 H5）：
```javascript
// pending_url 通过 URL 参数传递
const pendingUrl = new URLSearchParams(window.location.search).get('url');
if (pendingUrl) {
  // App 启动时读取这个 pending_url
  localStorage.setItem('tingxia_pending_url', pendingUrl);
}
```

#### F2: Android App Links 验证失败
**触发**：assetlinks.json 部署错误 / 证书变更没更新

**降级**：
1. App Links 失败 → 自动降级到 `intent://` URI Scheme
2. intent:// 仍然失败 → 浏览器打开 H5 引导页（同 F1）
3. assetlinks.json 部署检查 cron（每日验证）

#### F3: URL Scheme 拦截弹窗
**触发**：iOS 13+ 默认弹"是否在听匣中打开？"

**降级**：
- 用户选"打开" → 正常流程
- 用户选"取消" → 当前就失败了
- **优化**：监听 `onVisibilityChange` 检测用户取消 → 立即弹引导 toast"刚才的内容已为您暂存，下载/打开听匣继续"

#### F4: 微信灰度未生效
**触发**：用户微信版本 < 8.0.XX / 不在白名单

**降级**：
- 不在白名单 → 用户看不到"听匣"选项
- 引导：弹窗"微信版本过低？复制链接 → 浏览器 → 听匣"
- **关键**：避免"用户想用但不知道怎么办"流失

#### F5: Universal Links 缓存（iOS）
**触发**：App 卸载后 iOS 缓存没失效（最长 24 小时）

**降级**：
- 浏览器打开 → 自动检测 → 跳转应用商店（重新下载）
- 用户重装 App → `pending_url` 自动恢复

#### 10.7.1 4 阶段灰度 SOP（v1.2 新增 · Hornet 2026-09-09 拍板）

**为什么补这节**：原 §10.7 只有 6 步 bash 脚本，没有"5%→10%→50%→100%"各阶段的具体 SOP + 观察指标阈值——SRE 团队执行时不知道"5% 阶段观察多久、5xx 多高算异常"。

**4 阶段灰度框架**：

| 阶段 | 流量比例 | 持续时间 | 通过条件 | 回滚条件 |
|---|---|---|---|---|
| **G1 · 内部烟测** | 0%（仅 team）| 30 分钟 | 全部冒烟用例通过 | 任一冒烟失败 |
| **G2 · 5% 灰度** | 5% 真实流量 | 2 小时 | API 5xx < 1% / 蒸馏成功率不变 / 30 秒留存率不变 | 5xx > 1.5% 或留存降幅 > 5% |
| **G3 · 10% 灰度** | 10% 真实流量 | 6 小时 | G2 全部通过 + 告警无新增 | 同 G2 + P0 告警 ≥ 1 条 |
| **G4 · 50% 灰度** | 50% 真实流量 | 12 小时 | G3 全部通过 + 用户反馈无 P0 | G3 任一指标恶化 |
| **G5 · 100% 全量** | 100% | — | — | — |

**关键时间点**：
- **周末/节假日不上灰度**（人手不够响应）
- **大促/营销活动前 3 天不上灰度**（避免叠加风险）
- **周一早上 10 点不上灰度**（周末累积问题集中爆发）

#### 10.7.2 观察指标 + 阈值（每个阶段必看）

**核心 8 个指标**（每阶段都要看）：

| 指标 | 计算 | G2-G3 阈值 | G4 阈值 |
|---|---|---|---|
| **API 5xx 率** | sum(rate(http_5xx_total[5m])) / sum(rate(http_total[5m])) | < 1% | < 0.5% |
| **API P95 延迟** | histogram_quantile(0.95, http_duration_seconds) | < 1s | < 800ms |
| **蒸馏成功率** | sum(rate(distill_success_total[5m])) / sum(rate(distill_total[5m])) | 不变（±2%） | 不变（±1%） |
| **30 秒留存率** | listened_30s_total / distill_success_total | 不变（±5%）| 不变（±3%）|
| **错误日志新关键字** | log_diff（按关键字集合）| 0 新增 | 0 新增 |
| **OSS 写入成功率** | oss_write_success / oss_write_total | > 99% | > 99.5% |
| **Worker 崩溃次数** | ai_service_worker_crash_total | < 1/小时 | < 0.5/小时 |
| **支付成功率**（涉及支付的服务）| payment_success / payment_total | > 99% | > 99.5% |

**自动化判定脚本**（每 30 秒跑一次）：
```python
# scripts/canary/judge.py
async def judge_canary(metrics_window_5m):
    """返回: 'continue' / 'rollback' / 'manual_review'"""
    checks = [
        (metrics_window_5m.api_5xx_rate < 0.01, "API 5xx < 1%"),
        (metrics_window_5m.api_p95_latency < 1.0, "API P95 < 1s"),
        (metrics_window_5m.distill_success_rate_drop < 0.02, "蒸馏成功率降幅 < 2%"),
        (metrics_window_5m.listened_30s_drop < 0.05, "30秒留存率降幅 < 5%"),
        (metrics_window_5m.new_error_keywords == 0, "无新增错误关键字"),
    ]
    
    failed = [name for ok, name in checks if not ok]
    if len(failed) == 0:
        return 'continue'
    elif len(failed) >= 2 or any('蒸馏成功率' in f for f in failed):
        return 'rollback'
    else:
        return 'manual_review'
```

**自动化判定触发动作**：
- `continue`：继续下一阶段，发飞书通知"灰度 G2 通过"
- `rollback`：自动触发 `kubectl rollout undo`，发飞书告警"灰度自动回滚，原因：[失败项]"
- `manual_review`：发飞书给 SRE oncall，30 分钟内人工决定继续 / 回滚

#### 10.13.2 PostgreSQL PITR 演练（4 场景）

**演练环境**：**生产 RDS 同规格测试实例**（不是 dev/staging，配置差异太大）

**PostgreSQL PITR 恢复脚本**：
```bash
#!/bin/bash
# scripts/dr/pg_pitr_recover.sh
# 用法：./pg_pitr_recover.sh <target_time> "<db_name>"

set -euo pipefail

TARGET_TIME="${1:-2026-09-15T10:30:00+08:00}"
DB_NAME="${2:-tingxia_prod}"

echo "[1/5] 拉取最近一次基础备份..."
LATEST_BASE=$(aliyun rds DescribeBackups \
    --region cn-hangzhou \
    --db-instance-id rm-uf6xxx \
    --backup-mode Full \
    | jq -r '.Items.Backups | sort_by(.BackupStartTime) | last | .BackupId')

echo "  → 基础备份 ID: $LATEST_BASE"

echo "[2/5] 下载基础备份到临时目录..."
TMPDIR=$(mktemp -d)
aliyun rds RestoreDBInstance \
    --db-instance-id rm-uf6xxx \
    --backup-id "$LATEST_BASE" \
    --target-db-instance-class rds.mysql.s3.large \
    --vpc-id vpc-uf6xxx

echo "[3/5] 启动新 RDS 实例..."
NEW_INSTANCE_ID="rm-drf-$(date +%s)"
# 等待实例 status=Running（约 3-5 分钟）
while true; do
    STATUS=$(aliyun rds DescribeDBInstances --db-instance-id "$NEW_INSTANCE_ID" | jq -r '.Items.DBInstance[0].DBInstanceStatus')
    if [ "$STATUS" = "Running" ]; then
        break
    fi
    echo "  → 等待启动（当前: $STATUS）..."
    sleep 30
done

echo "[4/5] 应用 WAL 日志到目标时间点..."
# PITR 关键：指定恢复到的目标时间点
aliyun rds RecoveryDBInstance \
    --db-instance-id "$NEW_INSTANCE_ID" \
    --recovery-time "$TARGET_TIME" \
    --db-name "$DB_NAME"

echo "[5/5] 验证数据完整性..."
PGPASSWORD=$DR_PASSWORD psql -h rm-uf6xxx-${NEW_INSTANCE_ID}.pg.rds.aliyuncs.com \
    -U dr_checker -d "$DB_NAME" -c "
    SELECT 
        'users' AS tbl, COUNT(*) AS cnt FROM users
    UNION ALL SELECT 'articles', COUNT(*) FROM articles
    UNION ALL SELECT 'distill_tasks', COUNT(*) FROM distill_tasks
    UNION ALL SELECT 'quota_transactions', COUNT(*) FROM quota_transactions
    "

echo "✅ PITR 恢复完成 → 实例 ID: $NEW_INSTANCE_ID"
echo "📋 填写 dr_log 表，附上恢复耗时 + 数据校验结果"
```

**4 个 PITR 演练场景**：

| 场景 | 模拟故障 | 演练目标 | 期望 RTO | 期望 RPO |
|---|---|---|---|---|
| **PG-1：误 DROP TABLE** | 模拟"DELETE FROM articles WHERE author_id=X" 误执行 | 恢复 + 验证损失数据 | < 10 分钟 | < 5 分钟（找到误操作时间点） |
| **PG-2：磁盘损坏** | RDS 主实例模拟磁盘故障，需从备份重建 | 全量恢复 | < 30 分钟 | < 1 小时（最近全备） |
| **PG-3：AZ 不可用** | RDS 主实例所在 AZ 故障，需切到跨 AZ 副本 | 主从切换 | < 2 分钟 | 0（同步复制） |
| **PG-4：Region 不可用** | 整个 Region 挂掉，需从异地备份恢复 | 跨 Region 灾难恢复 | < 1 小时 | < 1 小时（异地 OSS + WAL） |

**PG-1 演练示例（最常见，每月必演）**：
```
演练步骤：
[1] 10:00 在生产测试实例执行 DROP TABLE articles_recycle_bin;
[2] 10:01 业务反馈"该表为空但 DELETE 报错"
[3] 10:02 SRE 启动 PITR 恢复脚本，指定恢复时间 = 09:59:30
[4] 10:08 新实例就绪，验证 articles_recycle_bin 表恢复
[5] 10:10 业务切到新实例（修改 ConnectionString）
[6] 10:12 恢复完成，填写 dr_log 表

实测：RTO=10 分钟 / RPO=30 秒（误操作时间点）
```

**PITR 时间窗限制**：
- RDS MySQL / PostgreSQL PITR 时间窗 = `最近一次基础备份时间 → 现在`
- 如果想恢复更早，需要拉更老的基础备份
- 保留策略：每天 1 次全备 + 每 6 小时 1 次增量 + WAL 归档保留 7 天
