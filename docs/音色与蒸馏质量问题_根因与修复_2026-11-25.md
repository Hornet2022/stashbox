## 1. 问题一：音色「换人感」

> ⚠️ **本节结论经过一次「换尺子」的返工**（这是本文最该记的一件事）。
>
> §1.5~§1.9 是**第一轮**的实验与判读，用的判据是「**段间基频散布**」。
> 那个判据在 §1.8 的噪声底实验里被**自己否掉了**（同文重渲就飘 14%）⇒
> §1.6 的 A/B 对比**作废**（不是「B 更差」，是**根本没测到东西**）。
>
> **§1.10 起**换成**身份层**判据（ECAPA）重做，结论与第一轮**相反**：
> **上下文续写被彻底否证**（第 4、5 块余弦掉到 0.05），
> 而**音域对齐自己**才是「换人感」的来源之一（治法比病更伤）。
>
> ⇒ 读这一节请**直接从 §1.10 开始**，§1.5~§1.9 当作「怎么走到换尺子这一步」的记录。

### 1.1 先纠正一个误解：「统一参考人声」**已经在做了**

用户提议「能否使用一个统一的参考人声，固化音色」。

核对代码：`app/services/tts/openai.py:857` 的注释写着
「⚠️ `clone` 必须是**逐块相同**的那一份参考音频」，实现上 `_clone_spec` 在 `synthesize()`
里解析一次、逐块传下去 ⇒ **每块确实带同一份 `ref_audio`**。

⇒ **「参考音不统一」不是病根**。真正的病根在下一层。

### 1.2 生产实证的完整因果链

```
上游每次请求 = 全新独立随机采样
  （openai.py:125 实测：同一句、同一 seed=42 连发两次，PCM 长度 168960 / 142080 bytes，
    差 19%；temperature=0 也不同 ⇒ seed 无效）
      ↓
各段音域随机漂
  生产实测（2026-11-24 journal 的「TTS 音高对齐」明细）：
      A 篇 4 段 f0_before：229.72 / 199.55 / 190.09 / 210.74 Hz  ⇒ 跨度 19%
      B 篇 3 段 f0_before：223.63 / 195.45 / 216.56 Hz
      ↓
事后用 rubberband 整体移调拉平（音域对齐，voice_align.align_pitch）
      A 篇位移：-1.64 / +0.80 / +1.64 / 0.00 半音
      B 篇位移：-1.17 / +1.17 / -0.61 半音
      对齐后误差 ≤ 0.9%（确实拉平了）
      ↓
但 ±1.64 半音 ≈ 移调 10% ⇒ 移调本身会染色
      ⇒ 听感上就是「音色变了」
```

⇒ **换人感 = 音域漂移的「补偿性染色」**。

ECAPA 身份层实测段间 0.60~0.77（同一人，没换人）⇒ **不是换人，是同一段音频里各段被移了不同量**。

### 1.3 对生产音频的独立实测

取生产最近一篇成品音频（`art_32c6abaf…`，314s，5 段），
用 `voice_align.f0_profile` 按 15s 窗口滑窗：

| 指标 | 范围 | 判读 |
|---|---|---|
| p50（中位数） | 182 ~ 231 Hz（±12%） | 整体音高**稳定** |
| p25（音域下缘） | 124.7 ~ 188.7 Hz | 波动大，但受文本/情绪影响大 |

⇒ 与 §1.2 一致：**不是「换人」，是「各段音域不齐 + 事后移调补偿」**。

### 1.4 治标方案（低风险，随时可上）

把音域对齐的锚点从「各段几何中点」改成「**首段 p25**」⇒ **首段位移 = 0**，
后续段相对首段微调 ⇒ 总染色下降。

⚠️ 契约 `docs/TTS音色一致性契约_v1.md` §2.3 已写明：
「±2.73 半音的位移本身也有染色代价 —— 段数变少后需要移的量也更小，
但**要不要给对齐设更小的死区/上限，待实测**」。

### 1.5 治本方案（上下文续写）与实验结论

**思路**（契约 §6 遗留第 1 条曾标注「先不做」）：
**让上一段当下一段的参考音** ⇒ 上游采样链式锁定 ⇒ 漂移从「每段独立」变成「随机游走」
⇒ 需要移的量骤降 ⇒ 染色消失。

**实验脚本**：`backend/scripts/exp_tts_contextual_continuation.py`（生产实跑）。
**实测数据**（生产真实听感稿 3175 字 → 5 块）：

| 组 | 各块 p25（Hz） | 段间散布 | 对齐位移（最大） |
|---|---|---|---|
| **A 现状**（同一份参考音逐块） | 188.3 / 170.1 / 169.7 / 168.1 / 190.6 | **13.4%** | 0.73 半音 |
| **B 上下文续写**（块N的输出当块N+1的参考） | 见下 | 见下 | 见下 |

⚠️ **实验踩到的硬约束**：上游对参考音有 **30 秒长度上限** ——
第一次跑 B 组直接被拒：

```
OpenAITTS 错误 400: backend_request_rejected
  Reference audio too long (114.7s). Maximum 30s supported — use a shorter clip.
```

⇒ 「整块输出当参考」**不可行**；改成**取上一块的前 30 秒 + 对应前段文本**当参考
（参考文本必须与参考音频内容对应，所以文本按同一比例截断）。

⇒ **B 组结论见 §1.6**。

### 1.6 B 组实测结果

**实验脚本**：`backend/scripts/exp_tts_contextual_continuation.py`（生产实跑）。
**文案**：生产真实听感稿 3175 字 → 切 5 块。

| 组 | 各块 p25（Hz） | 段间散布 | 对齐位移（最大） |
|---|---|---|---|
| **A 现状**（同一份参考音逐块） | 173.6 / 131.9 / 168.1 / 173.8 / 190.1 | 44.1% | 2.41 半音 |
| **B 上下文续写**（块N前30秒当块N+1的参考） | 152.3 / 154.4 / 138.1 / 102.4 / 136.9 | 50.8% | 2.98 半音 |

⇒ **表面上 B 更差 ⇒ 上下文续写没有可证明的收益。**

### 1.7 ⚠️ 但这个结论本身不可靠 —— 口径的重复测量方差太大

**同一份文案、同样的配置、只是换了个时间再跑一遍，A 组变成**：

| 轮次 | A 组段间散布 | 最大位移 |
|---|---|---|
| 第二次跑 | 13.4% | 0.73 半音 |
| 第三次跑 | **44.1%** | **2.41 半音** |

⇒ **差 3 倍** ⇒ A/B 之间那 6.7 个百分点的差异**落在噪声里，不构成证据**。

⇒ 这是「**度量本身要先校准**」的又一次复现（2026-10-22 已栽过一次）：
契约 §2.4 早就警告过「跨段比基频量到的是文案差异，不是换没换人」，
但没人量过「**同一段文本重渲**」的散布 —— 那才是这个口径的**噪声底**。

**因此本轮不据此改生产代码。** 先测噪声底（§1.8）。

### 1.8 噪声底实验（决定这个口径能不能用）

脚本：`backend/scripts/exp_tts_metric_noise_floor.py`
（**同一块文本**、同一份参考音、渲染 N 次，量每次 p25 的散布 ——
文案差异被消掉，剩下的才是「上游每次采样飘了多少」）。

**结果（当前上游，同一段 771 字文本重渲 4 次）**：

```
第 1 次：p25=174.6Hz  median=215.2Hz
第 2 次：p25=180.0Hz  median=232.5Hz
第 3 次：p25=196.1Hz  median=238.9Hz
第 4 次：p25=175.1Hz  median=209.5Hz

⇒ 同文重渲 p25 散布（噪声底）：12.3%
⇒ 同文重渲 median 散布：      14.0%
```

⇒ **噪声底 ≫ 5%（判据阈值）** ⇒ 「段间散布」这个量**主要在测噪声**。

⚠️ 对照：仓内 2026-10-24 的标定是「同一人 44s 片段散布 2.2~2.9%」。
⇒ **上游换过之后这套标定已作废**（当前上游同文重渲就飘 14%）。

### 1.9 判读：这个口径彻底不能用 ⇒ 换尺子

- 噪声底 14.0% ≫ 5% ⇒ 「散布」**区分不出任何东西** ⇒ §1.6/§1.7 的 A/B 比较
  **作废**（不是「B 更差」，是**根本没测到东西**）。
- 加上仓内既有结论（§1.7 引的契约 §2.4：「跨段比基频量到的是**文案差异**」）
  ⇒ 「段间基频散布」这条判据**两次被否**，不再使用。

⇒ **换尺子**：判据必须落在**身份层** —— ECAPA-TDNN 说话人嵌入余弦
（与音高、响度、文本无关）。仓内 `app/services/tts/consistency.py` 已经
把这条缝成契约（`ECAPA_SAME_MIN` / `ECAPA_DIFF_MAX` / `ECAPA_THRESHOLD`），
本轮**按当前上游重新标定**并复核。

⇒ 接下来的实验全部在身份层做（§1.10 起）。

### 1.10 ECAPA 身份层标定（当前上游，2026-11-25）

**素材采集**：`backend/scripts/exp_tts_identity_audit.py`（生产实跑）
+ `backend/scripts/exp_tts_identity_control.py`（对照组），
把每块的**原始音频**与**对齐后音频**落到磁盘 + `manifest.json`；
**判定在本机离线做**（生产 venv 没有 torch/speechbrain）。

**标定（克隆源 = 婷婷 = 上游预设音色 `uncle_fu`）**：

| 类别 | 实测区间 |
|---|---|
| 同一人（克隆块 vs 克隆源） | **0.857 ~ 0.931** |
| 同一人（不同文本的块 vs 块） | **0.931 ~ 0.978** |
| 同一人（同一段文本重渲两两） | **0.972 ~ 0.985** |
| 换人（上游预设音色两两 / vs 克隆源） | **0.357 ~ 0.697** |

⇒ 分离带 **[0.697, 0.857]**（中间是**空的**）⇒ 阈值 0.78。
⇒ 契约 §2.4 的旧值（0.75 / 0.35 / 0.55）**作废**：
两个**不同的**预设音色之间也能有 0.697（实测 `serena ↔ vivian`），
旧值会把「换人」误判成「不确定」。

### 1.11 上下文续写（B）：**彻底否证**

A 组（现状，逐块同一份参考音） vs B 组（块 N 的输出当块 N+1 的参考），
同一份 3175 字生产真实稿、切 5 块：

| | 各块 vs 参考音 | 块间相邻余弦 |
|---|---|---|
| **A 现状** | 0.862 / 0.858 / 0.880 / 0.871 / 0.912 | 0.971 / 0.978 / 0.971 / 0.931 |
| **B 上下文续写** | 0.856 → 0.764 → **0.656（不确定）** → **0.050（换人）** → **0.051（换人）** | 0.387（块3↔块4） |
| 同文重渲（噪声底） | 0.857 / 0.880 / 0.872 | 两两 0.972~0.985 |

⇒ **B 的声线在逐块崩塌**：第 4、5 块的身份余弦掉到 **0.05** —— 字面上就是换了个人。
⇒ 副作用：同样字数产出的音频**更长**（帧数 445 → 775 → 807 ⇒ 语速变慢）。
⇒ ⇒ **上下文续写不做**（契约 §6 里的「遗留」到此结案）。

### 1.12 音域对齐：**治法比病更伤** ⇒ 默认关闭

上游天然画出的音域差（同文重渲 3 次，音域散布 8.3% = **1.38 半音**）
在身份层是**无损**的：

| | 音域散布 | 块间身份余弦 |
|---|---|---|
| 对齐**前**（上游天然画的） | 8.3% | 0.9846 / 0.9791 / **0.9719** |
| 对齐**后**（各块移 ±0.69 半音抹平） | 1.9% | 0.8671 / 0.9404 / 0.9310 |

⇒ **Δ = -0.105** ⇒ 把音域拉齐了，音色反而更像「不同的人」。

**单块变调多少半音 ⇒ 身份掉多少**（本地实测，ECAPA）：

| 位移 | 0.25 半音 | 0.5 | 1.0 | 1.5 | 2.0 | 3.0 |
|---|---|---|---|---|---|---|
| 身份余弦 | 0.9946 | 0.9827 | 0.9386 | 0.8785 | 0.8114 | 0.7316 |

⇒ **同样的音域差，用「自然渲染差异」表达只掉到 0.972，用「变调」表达掉到 0.879
—— 变调比自然差异伤 3 倍。**

⚠️ **这个功能的原始前提被推翻了**：它当初要消除的是「音域差」，
并把「音域差」当成了「音色差」。而上游的音域差本来就是**不可消除**的
（重渲也飘 14%），所以它是在**追一个追不上的目标**，代价是逐块差异化处理。

⇒ **处置：音域对齐默认关闭**（`OPENAI_TTS_ALIGN_PITCH` 默认 `"0"`）。
⇒ ⚠️ **不是把封顶调小**：实测把封顶收到 0.5 半音后，死区（3%）几乎把功能
吃成空操作 —— 既修不掉真正的音域差，又连带废掉两条既有守卫
（「真的音域差仍要被对齐掉」）⇒ 正确的处置是**不跑**，不是**跑得小一点**。

### 1.13 接缝才是结构来源 ⇒ 块长 800 → 1500

仓内契约早就写明「**接缝 = 独立采样次数** =「一篇听出好几种音色」的来源」，
2026-10-25 也为此把块长从 250 提到 800。**当时的天花板是「旧上游有 60s 墙钟」
—— 这个前提在当前上游已经不成立**：

| 字数 | 墙钟 | 音频时长 |
|---|---|---|
| 800 | 34.5s | 115.5s |
| **1500（新）** | **63.0s** | **224.3s** |
| 1800 | 103.2s | 261.4s |
| 2000 | 77.7s | 274.0s |
| 2200 | 89.9s | 317.4s |
| 1400 / 1600 | — | **429「资源不足」** |

⇒ 我们的 httpx 读超时是 300s ⇒ 1500 字按最差实测斜率算仍有 **4.8 倍余量**。
⇒ **2500 字的稿子：4 块 → 2 块**（接缝 3 → 1）。
⇒ 不取 2200：收益只多一点点（3175 字 3 块 → 2 块），代价是单请求 90~103s、
上游一有负载就 429 ⇒ 余量比那一点接缝收益更值钱。

⚠️ **我自己第一轮的一个错误推断已撤回**：曾以为「上游有 ~322s 音频上限」
（三档音频时长精确相等）⇒ 复测发现**同一份 2000 字文本两次分别产出 322.0s 与
274.0s** ⇒ 那是**抽样语速**的差别，不是上限。

### 1.14 存量：**按流水线版本**划分，不是按时间窗

> ⚠️ **本节初版结论作废并已重写。**
> 初版写的是「95 篇里 18 篇（19%）在 p25 锚点 bug 窗口（2026-10-22 10:32 ~
> 2026-10-24 21:17）里合成 ⇒ 必须重生成」。
> **那个划法是错的**：它把「那段时间里生产的文章」当成了「那段时间里被 p25
> 对齐过的文章」。git 史显示两件事：
>
> * 音域对齐**接进流水线**是 `4c5989c`（2026-10-24 12:11）——
>   之前的 `8cd12fc`（10-22 10:32）只是把能力写进 `voice_align.py`，
>   `concat_mp3` 仍「默认跳过它」。
> * p25 → 中位数 的锚点切换是 `7a6676f`（2026-10-24 21:17）。
>
> ⇒ 真正吃过 p25 锚点的**只有 3 篇**（10-24 12:11~21:17 之间生产的）。
> 那个「18 篇」里的另外 15 篇**根本没接对齐**，它们的问题是**块长 250**（接缝极多）。

正确的划法是**按流水线版本**（`articles.created_at` 落到哪个版本的生效区间）。
关键分水岭不是 p25 锚点，而是**零样本克隆有没有真正生效**：

| 版本 | 生效区间 | 克隆（ref_audio 是否透传） | 音域对齐 | 克隆块长 | 篇数 |
|---|---|---|---|---|---|
| **V0** | ≤ 2026-10-24 14:45 | **未生效** ⇒ 上游每次请求**随机采样说话人** | 无 | 250 | **29** |
| V1 | 10-24 14:45 ~ 21:17 | 生效 | 有（**p25 锚点**） | 250 | 3 |
| V2 | 10-24 21:17 ~ 10-25 13:19 | 生效 | 有（中位数锚点） | 250 | 2 |
| V3 | 10-25 13:19 ~ 2026-11-25 | 生效 | 有（中位数锚点） | 800 | 61 |
| V4 | 2026-11-25 起（本次修复） | 生效 | **无** | **1500** | 重生成中 |

**V0 的 29 篇是「每块一个人」** —— 这条有当时的一手实测记录
（提交 `b0dd3b7`，2026-10-24 14:45）：

> 托管端点**不认 `voice` 这个说话人名**。同一段文本、同一个 `voice=uncle_fu`
> 连发 3 次，基频中位数 **165.0 / 188.5 / 105.3 Hz** —— **三个不同的人**。
> 我们按 700 字分块 → 每块一次请求 → **每块一个人**。

⇒ 克隆没透传 `ref_audio` 时，上游每次请求都重新随机采一个说话人，
**块长只是把「一篇几个人」变成「一篇十个人」的乘数**。

V1~V3 的 66 篇则是另一类问题：克隆生效后**身份有了锚点**，但块长仍小
（250 / 800 字 ⇒ 一篇 3~10 个接缝），每个接缝都是一次身份跳变的机会，
再叠加音域对齐（人为变调）额外制造身份差。

⇒ 95 篇**全部**是「多次独立渲染 + 多接缝」的产物 ⇒ **全部需要重新核验**，
不能只挑某 18 篇。核验结果见 §1.16。

⇒ 重生成走生产同一条蒸馏路径（`scripts/redistill_voices.py --apply --article …`），

## 2. 问题二：播放列表「无音频资源」（已修）

### 2.1 现象

蒸馏中的文章加进播放列表 → 蒸馏完成 → 从播放列表点播放 → 「这一篇还没有音频，蒸馏好了才能播」。

### 2.2 根因（两条，都不是服务端不给地址）

**根因 A：补齐逻辑不被「蒸馏完成」驱动**

`PlaylistViewModel.backfillMissingMetadata` 挂在 **Room 表变化**上（`init` + 用户操作列表），
而**蒸馏完成不写本机表** ⇒ observer 不 emit ⇒ 补齐永远不被触发。

**根因 B：补齐走的是 20 篇分页的列表接口**

原实现调 `articleRepository.getArticles()`（后端 `GET /api/v1/articles` 默认 `limit=20`，
只返回最近 20 篇）再在内存里按 id 匹配 ⇒
播放列表里那篇若是老文章，**永远匹配不上** ⇒ 地址永远补不上。

⇒ 症状从「暂时播不了」变成「**一直**播不了」。

### 2.3 修复：按 id 现取（回到设计契约）

`PlaylistRepository` 的类注释本来就写着「**只存 id，播放时现取地址**」，
但 `add()` 存了快照、`playFrom` 只读快照 ⇒ **实现偏离了自己的设计契约**。

改动（`stashbox-android`）：

| 位置 | 改动 |
|---|---|
| `backfillMissingMetadata` | 改成按 id 调 `getAudioUrl(articleId)`（单篇端点，不受分页限制、数据是当下的）；未就绪时后端 404 ⇒ 兜住、不写 |
| `playFrom` | 快照为空 ⇒ **现取一次**：取到就播并把新地址写回快照；取不到才提示 |

### 2.4 护栏（4 例 + 变异 2/2）

`app/src/test/kotlin/com/tingxia/audio/ui/playlist/PlaylistViewModelTest.kt`：

| 用例 | 钉住的契约 |
|---|---|
| 快照为空且已就绪 ⇒ 点播放要现取地址并播出去 | 核心修复 |
| 快照为空且还没蒸馏好 ⇒ 不播且说清楚原因 | 不播空地址 |
| 快照非空 ⇒ 点播放不额外发请求 | 别把每次播放变成网络往返 |
| 补齐不受文章列表分页限制 ⇒ 老文章也能拿到地址 | 根因 B |

⚠️ **第一版守卫是假绿的**（变异打不掉）：测试里把 `api.ready = true` 写在 `vm()` 构造**之前** ⇒
init 的补齐先把地址填上了 ⇒ `playFrom` 走的是「快照非空」分支，**根本没进现取分支**。
⇒ 改成「先建 VM（未就绪）→ 再置就绪 → 再点播放」，才真正覆盖真实场景
（页面开着、蒸馏后来完成、用户这时才点播放）。

**变异检验**：

| 变异 | 期望变红 | 结果 |
|---|---|---|
| M1：`playFrom` 退回「快照空 ⇒ 直接提示不播」 | 「已就绪能播」那条 | ✅ 精确命中（其余 3 条仍绿） |
| M2：补齐退回「拉 20 篇列表再匹配」 | 「补齐不受分页限制」那条 | ✅ 精确命中 |

全量：安卓端 **495 passed**。提交 `ad7e192`。
