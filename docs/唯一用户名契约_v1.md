# 唯一用户名（username）契约 v1 — 2026-11-27

> 状态：**已实现，待部署**（后端迁移 0043 + 安卓 0.5.7 上报设备特征）
> 单一真相源：代码在 `backend/common/username.py`，文档只解释「为什么」，
> **规则本身不在文档里重复定义**（避免两处漂移）。要改规则，改代码常量 + 守卫。

---

## 1. 问题：内测账号全都叫「听友」

`users.nickname` 是**显示名**，不是标识。微信登录建号时它是硬编码常量
（`backend/user-service/main.py` 建号分支 `nickname="听友"`）⇒ **所有内测账号昵称都一样**。

而 `users` 表既没有 nickname 唯一约束、也没有它的索引 ⇒ 管理后台按昵称搜不出
「是哪一个」，两张同名「听友」在运营眼里是同一个人；导出 CSV 同样分不开。

⇒ 需要一个**全局唯一**、运营能一眼看出是谁的标识。

## 2. 缝合定义：三个概念各归其位

过去"名字"这个词混着三件事，这次拆开（**别再混用**）：

| 概念 | 存哪 | 唯一性 | 给谁看 | 本轮决策 |
|---|---|---|---|---|
| 显示名 | `users.nickname` | **可重复**（现实中大家都叫小明） | 人 | **不动**（用户拍板"默认昵称不动"） |
| **唯一用户名** | `users.username`（本契约） | **全局唯一** | 后台 / 本人 | 新增 |
| 设备指纹 | **不落库**，客户端登录时上报 | 设备内恒定 | 只作生成输入 | 只读不存 |

设备指纹**不落库**的原因：它由 ANDROID_ID 派生，属于设备标识而非用户资料；
落库会带来额外的个人信息留存面。它只是 username 的**输入**。

## 3. 取值规则（v1 = 设备派生）

    d-<机型10位>_<设备指纹8位>      例：d-XIAOMI14PR_3F9A2C71

* **机型**：客户端上报 `Build.MANUFACTURER + Build.MODEL` ⇒「具备特征性」：
  后台一眼看出是谁的哪台机器。规范化 = 去非字母数字 → 转大写 → 截断 10 位
  （机型名带空格与中文，如 "Redmi K80 5G"）。
* **设备指纹**：客户端上报 `DeviceId.androidIdSuffix()`（= SHA-256(ANDROID_ID) 前缀，
  跨重装恒定）或 `DeviceId.analyticsDeviceId()`（`and-…` / `rnd-…`）。
  规范化 = **去来源前缀** → 去非字母数字 → 转大写 → 取**开头** 8 位。
* **取不到机型/指纹时**：回落 `t-<用户id>`（`t` = 兜底形态）。

### 3.1 为什么指纹取「开头 8 位」而不是「末 8 位」

三种上报形态的**本体长度不同**（`and-` 12 位 / `rnd-` 16 位 / 裸 12 位）：

* 先去前缀再取**开头** ⇒ 本体长度无关 ⇒ **同一台设备不论上报哪种形态都得到同一个指纹**
  ⇒「同一台设备恒定同一个 username」成立。
* 按整串取末位 ⇒ 取位随本体长度漂移（12 位与 16 位末 8 位不是同一段）
  ⇒ 同一台设备可能因为上报形态不同而拿到两个用户名 ⇒ 契约破。

守卫：`tests/user/test_username.py::test_同一设备不同上报形态得到同一指纹`。

### 3.2 形态前缀一览

| 前缀 | 含义 | 何时产生 |
|---|---|---|
| `d-` | 设备派生（暂用形态） | 登录时客户端上报了设备特征 |
| `t-` | 兜底形态（无设备信息） | `t-<用户id>`；ORM 层随机兜底 `t-<随机hex>` |
| `w-` | 微信派生 | 微信登录上线后（v1 未使用） |

`d-` 的连字符与仓内 `and-` / `rnd-` 约定同源 —— 让后台一眼看出 id 的来源。

## 4. 唯一性：最终由 DB 保证

* **DB 层**：唯一索引 `uq_users_username_lower` 建在 `lower(username)` 上
  （表达式索引，迁移 0043）⇒ **大小写不敏感**。
  用普通 unique 索引的话 `Ting_23` 与 `ting_23` 能同时入库 ⇒「唯一」名存形同虚设。
* **应用层**：`common/username.assign_username()` 依次尝试候选
  `d-…` → `d-…-2` → `-3` … → `t-<id>`。
  冲突时用 `db.begin_nested()`（SAVEPOINT）—— 唯一索引冲突会把**整个事务**打成
  aborted，直接重试必然二次失败；SAVEPOINT 只回滚到保存点，外层事务（用户的 INSERT）仍活着。
* **INSERT 永不冲突**：ORM 层 `username` 的 default 是随机兜底（`t-<随机hex>`），
  所以建号 INSERT 本身不会撞索引；需要换名的只有随后的 UPDATE（走 SAVEPOINT 重试）。

## 5. 端点口径

| 端点 | 变更 |
|---|---|
| `POST /api/v1/auth/wechat-login` | 请求新增**可选** `device_id` / `device_model`；建号时生成 username。旧客户端不传 ⇒ 回落 `t-<id>`，唯一性照样成立 |
| `GET /api/v1/user` | 响应新增 `username` |
| `GET /api/v1/auth/me` | 响应新增 `username`（与上者**同一口径**） |
| `GET /api/v1/admin/users` | 列表项新增 `username`；`keyword` 搜索纳入 username（昵称全是同名时，运营唯一的区分手段） |
| `GET /api/v1/admin/export/users.csv` | 导出表新增 `username` 列（表头与行同步，列位在 `display_name` 之后） |

> 两个 me 端点的 **nickname** 兜底口径仍不一致（`听友_{id}` vs `听友`）——
> 这是**显示名**的兜底，本轮**不改**（用户已拍板"默认昵称不动"）；
> 本轮统一的是 **username** 这一条。

## 6. 客户端上报什么（零新增权限、零新增采集）

安卓端复用**既有**资产，不新采任何数据：

* `util/DeviceId.androidIdSuffix()` = `SHA-256(ANDROID_ID)` 前 12 位
  —— ANDROID_ID 是系统自带，**不需要任何运行时权限**；同一 App 签名 + 同一手机用户下跨重装恒定。
* `Build.MANUFACTURER + Build.MODEL` —— 机型，零权限。
* 取不到可靠 ANDROID_ID 时回落 `analyticsDeviceId()`（`rnd-…`，仅本机安装内稳定）。

⚠️ `KNOWN_BAD_ANDROID_ID`（部分定制 ROM 的常量 `9774d56d682e549c`）已被既有代码排除，
不会拿它当设备指纹 ⇒ 不会出现"所有设备同一个用户名"。

## 7. 迁移 0043 的行为

* 加列 `username VARCHAR(32) NOT NULL`（先 nullable 加列 → 回填 → 再置 NOT NULL）。
* **回填规则**：统一 `t-<id>`。**不回填设备形态** —— 迁移时拿不到设备信息
  （设备特征只在登录时上报、服务端库里没有）⇒ 存量用户拿兜底名，新登录用户拿设备形态名。
  两者都唯一，只是形态不同。
* 建唯一索引 `uq_users_username_lower`（表达式索引）。
* **不写"不可变"约束**：微信登录上线时 username 会整体迁移（设备派生 → 微信派生）⇒ 必须可改。
* 本列**不含个人信息**：由设备指纹哈希派生，不是原始 ANDROID_ID。

## 8. 已知边界

* 存量账号是 `t-<id>` 形态，可读性差一点；要不要手工订正由运营侧一次性数据订正决定。
* 同一台设备若因指纹异常而建了两个账号，第二个会拿到 `d-…-2`（唯一性仍成立，可读性变差）。
* `t-<用户id>` 与 `t-<随机hex>` 同属兜底族：前者是"按 id 兜底"，后者是"ORM 层随机兜底"。

## 9. 微信登录上线后怎么办（v1 不做）

1. 客户端改报微信派生信息 ⇒ 服务端改用 `w-` 前缀形态。
2. 存量 username **整体 UPDATE** 到 `w-` 形态（列可改，无不可变约束 ⇒ 直接改即可）。
3. 设备形态 `d-` 与微信形态 `w-` 一眼可辨 ⇒ 迁移结果可核对。

## 10. 守卫在哪

`backend/tests/user/test_username.py`（15 例）：

| 组 | 锁住什么 |
|---|---|
| A | 纯函数：机型规范化、指纹去前缀取开头、**同设备不同上报形态同指纹**、取值形态、候选序列、合法性校验 |
| B | DB 层：唯一索引真的挡住重复、**大小写不敏感** |
| C/D | 登录建号：设备形态 / `t-<id>` 回落 / 同设备重登**用户名不变** |
| D2 | 同设备两个账号 ⇒ 第二个自动降级 `-2`（SAVEPOINT 重试路径） |
| E | admin 列表能按 username 搜到 |
| F | 两个 me 端点返回同一 username |

另有 `tests/admin/test_export_csv.py` 锁住 CSV 的 username 列（表头 + 行值）。

⚠️ 守卫**不依赖"库是干净的"**：测试库持久、跨轮次不清 ⇒ 用例用当轮随机设备指纹，
期望值由 `build_username()` 算出（既钉死形态，也钉死"同形态同来源 ⇒ 同名"）。

## 11. 部署顺序（不可颠倒）

1. **先**跑迁移 0043（加列 + 回填 + 唯一索引）—— 老代码不读这一列，跑迁移安全。
2. **再**部署后端新代码（读 username、生成 username）。
3. **再**发安卓新版（开始上报 device_id / device_model）。

⚠️ 为什么必须这个顺序：

* **迁移必须在新后端之前**：新代码读 `users.username` ⇒ 列不存在会直接 500。
* **迁移早于新后端是安全的**：老代码不碰这一列。
* **安卓发版与迁移互不依赖**（老服务端会忽略它不认识的 `device_id`/`device_model`，
  Pydantic 默认忽略多余字段）⇒ 但要让新账号拿到 `d-` 形态，
  安卓新版必须在**后端新代码之后**（或至少同时）上线。
