# 剪藏「网络连接失败」复盘与后台抓取改造（2026-11-11）

> 内测反馈：**用 App 剪藏时碰到多次网络连接失败的提示，关闭应用重新打开后又正常了**（uid 23）。
>
> 本文记录：取证 → 根因 → 两层修复 → 顺带挖出来的三个口径坑 → 护栏 → 上线验证。

---

## 1. 现象

- uid 23 在 2026-11-11 17:40~17:43 连续剪藏 4 个微信链接，客户端反复弹「网络连接失败」。
- 用户自己发现：**关掉 App 重开就好了**，文章其实已经建好、已经在合成音频。
- 客户端侧当时只有 logcat，**没有任何埋点** ⇒ 事后只能靠 nginx 反推。

---

## 2. 取证（先看事实，再下结论）

| 观察面 | 证据 | 结论 |
|---|---|---|
| nginx API 专用日志 | `/var/log/nginx/stashbox.access.log`：4 次 `POST /api/v1/articles` **全部 200**，rt 1.7~2.3s，UA `okhttp/4.12.0`，源 IP `113.57.86.191` | 服务端**全部成功** |
| 数据库 | 4 篇文章**全部建好**，worker 正常合成（j_failed=0） | 不是「没收到」 |
| 全天该 IP 的请求 | 85 个请求**全部 2xx**，抓取失败 0 条 | 不是服务端抓取失败 |
| 客户端实现 | 剪藏失败只有一个来源：`CaptureViewModel.capture()` 里 `createArticle` 抛异常；响应模型字段**全 nullable**（不会解析失败）；超时 65s（不是原因） | 失败发生在**客户端本地**（没收到/没解析到响应） |

⇒ **服务端零感知**。这不是「服务端抓不到网页」，是「**服务端成功、客户端报错**」。

---

## 3. 根因：剪藏接口是「同步长请求」

改造前 `POST /api/v1/articles` 会**当场抓取**（HTTP 退避重试 + 无头浏览器兜底，整条降级链最坏 ~40s），
客户端一直等这个响应。**客户端等的这段时间里，任何客户端侧抖动**（切网、NAT 回收、HTTP2 流重置、
后台调度、连接池复用）都会变成「服务端已经建好文章，客户端却收到失败」。

用户视角就是：**反复失败 → 重试 → 再失败**（每次重试都把这条长链再走一遍）。

### 为什么不能只靠「重试」

重试会把「服务端成功、客户端报错」变成「重复建文章 / 重复扣配额」的风险面。
即使 URL 去重能挡住重复建文章，**每一次重试仍要再走一遍抓取**。

---

## 4. 第一层修复（0.5.4 已含）：失败时**回查**，而不是一律说失败

- 服务端新增 `GET /api/v1/articles/by-url?url=`（按 URL 幂等回查，口径复用 `_find_existing_clip`，
  与剪藏时的早查重**同一份实现**）。
- 客户端失败时回查一次，得出**三结局**（`CaptureFailure` 纯函数）：
  - `SUCCEEDED` —— 其实成功了 → 告诉用户「已提交，正在处理」，并继续轮询；
  - `FAILED` —— 真失败 → 显示服务端给的**具体原因**；
  - `UNKNOWN` —— 连回查都失败 → 说「待确认」，**不能**让用户以为失败而重复剪藏。
- 失败事件补埋点 `article_capture_failed`（此前只有 logcat ⇒ 服务端零记录）。

> 这一层治的是「**说错话**」；下一层治的是「**别让客户端有机会说错话**」。

---

## 5. 第二层修复（本次）：剪藏接口改成**后台抓取**

### 方案

```
POST /api/v1/articles
  ├─ 早查重 ──► 有正文            ⇒ 复用（沿用旧行为：必要时重派蒸馏）
  │           ├─ 正在抓（in-flight）⇒ 返回同一篇，**不重复驱动**
  │           └─ 没正文没人抓     ⇒ **重新驱动抓取**（失败过 / 进程重启留下的孤儿）
  ├─ 配额只读检查（用尽 ⇒ 立刻 403/3001，**不建行**）
  ├─ 建 pending 行（raw_content 留空 = 「抓取中」）
  └─ 立即返回 {article_id, status:"pending", fetch_pending:true, quota_pending:true}

后台任务（content-service 进程内 asyncio 任务）
  ├─ 抓取 ──► 成功 ⇒ 写正文 + **扣配额**（先抓后扣）+ 打配额标记 + 派蒸馏
  │         └─ 失败 ⇒ status=failed + **面向用户的中文原因**（articles.error），**不计费**
  └─ 结束（成功/失败/跳过）⇒ **清掉在跑标记**

兜底定时器（lifespan，每 60s）
  └─ pending 且**没有正文**且**没有在跑标记**且已超时 ⇒ 标记 failed（抓取超时，请重试）
```

### 为什么是这个方案（而不是新建跨服务队列）

抓取代码本来就在 content-service 进程里；队列化只是把「一个函数调用」变成
「一次跨服务 RPC + 一张队列表 + 一个消费者」，而跨机扩展当前并不存在。

### 三条不能破的语义

| 语义 | 口径 |
|---|---|
| **先抓后扣** | 抓不到正文 ⇒ **不扣配额**（2026-10-03 定的口径，后台化之后依然成立） |
| **不重复计费** | 抓取中重复提交 ⇒ 同一篇、只扣一次 |
| **缺席必须点名** | 抓取失败要在文章上写**面向用户的中文原因**，不能变成「永远 pending」 |

### 接口契约的变化（诚实优先）

`POST /api/v1/articles` 的回执新增两个布尔：

- `fetch_pending` —— 抓取在后台进行中；
- `quota_pending` —— **本次配额尚未扣除**（抓到正文才扣）。

回执里的 `quota_used` 从「本次剪藏扣了几次」变成「**提交这一刻**的用户配额快照」
（不含本次的后台扣减）。理由：扣费发生在响应之后，写成 1 等于**宣称已经扣了**，
而抓取失败时其实不会扣。客户端以刷新后的配额为准。

### 生产验证（2026-11-11 18:42）

| 观察点 | 结果 |
|---|---|
| `POST /api/v1/articles` 耗时 | **0.268s**（改造前是秒级~几十秒） |
| 回执 | `status=pending`、`fetch_pending=true`、`quota_pending=true` |
| 后台抓取结果（example.com 抓不到正文） | `status=failed`、`error="这篇文章已被删除或链接已失效"` |
| 配额 | **没扣**（uid 23 的 quota_used 保持 13 不变） |

## 6. 顺带挖出来的三个口径坑（都是「静默失效」型）

### 6.1 `raw_content` 是 JSONB：Python `None` 落库是 **JSON null**，不是 SQL NULL

实测：`SELECT raw_content, raw_content IS NULL FROM articles` → `(None, False)`。
⇒ 只判 `IS NULL` 会把「**从没抓到正文**」判成「**有正文**」
⇒ 后台抓取会以为已经抓过而跳过 ⇒ 文章**永远 pending**；兜底定时器也永远扫不到它。

⇒ 判据统一到**一处**：`common/models/article.py::NO_RAW_CONTENT`
（`IS NULL` **或** `jsonb_typeof(...) = 'null'`）。Python 侧仍是 `article.raw_content is None`（两种都读成 None）。

### 6.2 兜底定时器的年龄必须由 **DB 时钟**算

`created_at` / `updated_at` 落库用 PG 的 `now()`（**server timezone**），而 Python 侧是 UTC：
本地开发机 PG 是 UTC+8 ⇒ 实测库里 created_at=18:12、UTC=10:12
⇒ 「2 小时前的孤儿」被算成「还差 6 小时」⇒ **兜底定时器永远扫不到任何东西**。

⇒ 年龄一律由 DB 算（`now() - updated_at`），Python 只做阈值比较（`is_fetch_stale`）。
另外用 `updated_at` 而不是 `created_at`：后者会把「两天前创建、今天重新驱动抓取」的文章立刻当孤儿杀掉。

### 6.3 测试环境里 Redis 连接池跨事件循环 ⇒ 「Redis 挂了」的假象

`common/redis_client.get_redis_pool()` 是模块级全局池，而 redis-py 的连接绑定**创建它的事件循环**；
pytest 每条用例一个新事件循环 ⇒ 旧连接在新循环里用就抛
「got Future attached to a different loop」/「Event loop is closed」，
报错点在业务代码里（实测是鉴权里的 `client.get`），看起来像 Redis 挂了。

⇒ 新增 `common/redis_client.reset_redis_pool()`，测试在每条用例前重置池（生产是单事件循环，不受影响）。

## 9. 遗留与后续

1. **并发上限**：content-service 内存上限 224MiB（`MemoryMax`），后台抓取与请求共享同一进程。
   当前没有并发闸 —— 极端情况下多个剪藏同时抓会抬高峰值。**下一轮要加**（信号量 + 拒绝快返）。
   ✅ **已做（2026-11-11 下一轮）**：并发闸门（信号量 + 拒绝快返）已落地 ——
   并发上限 `CAPTURE_MAX_CONCURRENCY`（默认 4，env `STASHBOX_CAPTURE_MAX_CONCURRENCY` 可调），
   满则**拒绝快返**（不排队）：新剪藏 / 早查重 refetch / retry 三个触发点被拒时，
   文章标 `failed` + 中文原因「当前抓取繁忙，请稍后重试」，**不扣配额**（先抓后扣）。
   抓取结束槽位归还（`run_capture_fetch` 的 `finally`）。新增 6 例测试 + 4 条变异（M10–M13），
   变异检验 13/13 全捕获。
2. **多 worker**：本单元是单进程（systemd 没传 `--workers`）⇒ 兜底定时器只有一个。
   若将来上多 worker，定时器会跑多份（判定幂等，但要挪到独立进程）。
3. **抓取失败的分类**：目前只区分「失败」与「超时」，还没有按 source 细分用户文案
   （`fetch_error_user_message` 已有那套话术，失败分支复用了它，但可以更细）。
