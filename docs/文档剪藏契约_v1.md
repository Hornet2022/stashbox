# 文档剪藏 · 契约 v1（2026-10-23）

> 状态：**已实现（后端）**，安卓端 / 管理后台 / 改写 prompt 分支待做。
> 本文是「缝合定义」—— 后面几端的改动都按这里打补丁，不要各自发明。

## 0. 一句话

**文档剪藏 = 用户提交一份文档（文件或粘贴文本）→ 解析成与抓取同形的正文 → 走**现有剪藏链路**的后半程。**

关键设计：**`articles.raw_content` 的形状不变**（仍是 `FetchResult` 同形），
所以蒸馏、订阅推送、TTS 全链路**零改动**。

## 1. 为什么单独一个端点

现有 `POST /api/v1/articles` 的轴是 **URL**（`get_fetcher(url)` → 抓 → 建库）。
文档没有 URL。硬塞字段就要在链路中间插分叉，而分叉插在链路中间，
后面每一环都要记得「这次没有 fetcher 结果」。

所以分叉放在**链路之前**：

```
链接剪藏：URL → fetcher 抓 ─┐
                            ├→ 正文（FetchResult 同形）→ 去重 → 扣配额 → 建库 → 派蒸馏 → 失效缓存
文档剪藏：文件 → 解析器 ────┘
```

后半程**只有一份实现**（`_clip_after_fetch`）。

## 2. 端点契约

`POST /api/v1/articles/document`（multipart/form-data）

| 字段 | 类型 | 说明 |
|---|---|---|
| `file` | 文件（可选） | 文档二进制 |
| `text` | 文本（可选） | 直接粘贴的 Markdown / 纯文本 |
| `title` | 文本（可选） | 不填则从文档推断 |

* `file` 与 `text` **二选一**；都为空 → 400；都传 → 400。
* 响应与 `POST /api/v1/articles` 同形，另加 `reused` / `filename` /
  `content_type` / `text_length` 四个诊断字段。

### 与链接剪藏的语义对齐（逐条）

| 语义 | 链接剪藏 | 文档剪藏 | 共同实现 |
|---|---|---|---|
| 先拿正文后扣费 | 抓取失败 → 2002，不建库不计费 | 解析失败 → 2002，不建库不计费 | 同口径（2026-10-03 定的） |
| 去重 | 同 user + 同 url | 同 user + 同 **内容 hash** | `_find_existing_clip` |
| 扣配额 | 建库前 | 建库前 | `quota_service.consume` |
| 标记已扣费 | `mark_article_quota` | 同 | 同 |
| 派蒸馏 | `trigger_distill` | 同 | 同 |

## 3. `articles` 表：**不改**

| 列 | 文档剪藏怎么填 |
|---|---|
| `url` | `doc://{sha256[:16]}`（**内容 hash**）→ 同一份文档重复上传天然复用同一篇 |
| `source` | `"document"`（新码值，与 `web`/`wechat`/`pdf` 并列） |
| `title` | 请求的 title，否则从文档推断（文件名 → 首个 Markdown 标题 → 首个非空行） |
| `raw_content` | `FetchResult` 同形（`content_text` / `content_html` / `title` / `raw_metadata`） |
| `raw_content.raw_metadata` | 额外放 `filename` / `content_type` / `bytes` / `sha256` / `parser` / `text_length` / `truncated` / `page_count` |

**为什么不改表**：加列就要写 alembic 迁移，而新列对下游没有任何用处
（正文已经在 `raw_content` 里，且列表端点本来就把这列 defer 掉）。
不改表 = 零迁移风险。

**为什么 `url` 用内容 hash 而不是文件路径**：
`url` 有 NOT NULL 约束，而「同一份文档」的天然身份是**内容**不是文件名
（同一份 PDF 改名后仍是同一份）。用 hash ⇒ 去重语义正确，且不需要新列。

## 4. 支持的格式（第一版）

| 格式 | 解析方式 | 新依赖 |
|---|---|---|
| PDF | 复用 `fetchers.pdf.extract_pdf_text`（**与 PDF 直链抓取同一份逻辑**） | 无（pypdf 已有） |
| Markdown / TXT / CSV / JSON / YAML | 直接解码（utf-8 → gb18030 → 兜底 replace） | 无 |
| HTML | 复用 `fetchers.parser.ContentExtractor`（**与网页抓取同一份抽取器**） | 无 |
| DOCX | **标准库** `zipfile` + `xml.etree`（读 `word/document.xml` 的 `<w:t>` 节点，按 `<w:p>` 换行） | 无 |

**不支持**：扫描件 PDF（无文本层）、加密 PDF。→ 与现有 PDF 直链抓取**同样不支持**
（文档剪藏不该比「剪藏一个 PDF 链接」更宽松或更苛刻）。

> **为什么不引入 python-docx**：仓里除 pypdf 外没有第二个文档解析依赖，
> 而 DOCX 的正文抽取用标准库几十行就够。引入新依赖要过依赖评审，
> 收益不匹配。

## 5. 长度控制（两个维度）

| 维度 | 上限 | 超出时 |
|---|---|---|
| 上传文件大小 | **10MB** | 端点 400 + 明确文案（**与 nginx `client_max_body_size 10m` 同口径**） |
| 正文长度 | **200,000 字符** | **截断 + `raw_metadata.truncated=True` + warning 日志** |

* **文件上限必须与 nginx 一致**：端点比网关宽 → 用户先撞网关 413（没有信息量）；
  端点比网关窄 → 用户撞我们自己的提示（能说清为什么）。取 10MB，两边一致。
* **正文上限比网页的 50KB 大**：网页那个是「防爆」口径，文档是用户**特意**提交的
  内容，砍掉就是骗人。
* **截断必须可观测**：网页那侧是静默砍的（`parser.py` 的 50KB），
  文档不能这样 —— 用户会得出「这份文档没有我要的信息」的错误结论。

## 6. 错误话术

`fetch_error_user_message` 新增 `source == "document"` 分流：

* `PARSE` → 「没能从这个文档里读出文字。如果是扫描件（图片版 PDF）或加密文件，
  我们暂时读不了，可以换个文件或直接粘贴文本试试」
  （**不**沿用链接那句「页面可能需要登录」—— 文档没有「登录」这回事）
* `UNSUPPORTED` → 「暂时不支持这个文档格式，可以换个文件或直接粘贴文本试试」

## 7. 网关

* `api-gateway/config.py` 显式注册 `POST /api/v1/articles/document` → content-service
  （`articles` 前缀在兜底白名单里能通，但**显式注册**才走完整路由表匹配 ——
  这个仓已因「实现了但没进路由表 → 404」踩过四次）。

### 8.3 改写 prompt 分支（**没有它，文档剪藏会出「胡话」**）

`_REWRITE_SYSTEM`（`ai-service/agent/runner.py:686-786`）现在假设输入是
「一篇公众号文章」，具体不适配：

| 契约点 | 原文 | 对文档/代码库的问题 |
|---|---|---|
| 任务定义 | 「把**原文**改写成…希望快速吃透**一篇文章**要点的人」 | 输入不是「一篇文章」 |
| hook | 「**钩子要狠**…可以是反问、矛盾、或出人意料的对比」 | 文档没有钩子感 → **逼出编造** |
| outro | 「**收束呼应**：呼应 hook 的开头意象」 | 文档无叙事线可呼应 |
| 不要复读 | 「**不要复读原文**，要重述 + 加你的解读」 | README 的价值恰恰是**准确复述**用法 → 与下面「有依据」自相矛盾 |
| 长度自适应 | 「> 2000 字 → 1000-1400 字」 | 文档常 5k-50k 字 → 与「不要漏点」**直接冲突** |
| 代码块 | 无「不要念代码块/命令/路径」的约束 | `pip install x` 会被念成「派 pip install」 |
| 标签 | 「必须从候选标签里原样选」 | 代码库主题（Python/数据库…）大概率不在 `tags` 表候选里 → **订阅推送彻底失效** |

⇒ 需要：按「素材类型」（文章 / 文档 / 代码库）分支 prompt；
`state["source"]` **已经在 initial_state 里**（`distill_task.py:924`），可直接用。

### 8.4 长文档的两个隐患

1. **max_tokens**：agent 改写**不传 max_tokens** → 吃默认 4096
   ⇒ 文档稿（1000-1400 字 + JSON 结构）**可能被截断成非法 JSON**
   → `_extract_json_object` 失败 → 降级成纯文本按空行切（稿子结构全丢）。
   **要显式设 max_tokens。**
2. **上游丢 content**：历史记录「2925 字 prompt 非流式 4/4 空」，改成流式后已解决，
   但**没有 >20k 字输入的生产样本** —— 文档场景会显著放大这个风险面。

## 10. GitHub 开源库剪藏（**本轮未做**）

调研结论：**全仓零实现、零规划**（backend 无任何 GitHub API 调用）。

**它比文档剪藏便宜得多**，因为它是「**剪藏一个 URL**」：
只需要一个 `fetchers/github.py`（抓 README + 仓库元信息：stars / 语言 / 描述），
`source="github"`，然后**复用现有整条 URL 剪藏链路**（去重/扣费/建库/派蒸馏全不动）。

⇒ 建议顺序：**文档剪藏（后端已就绪）→ prompt 分支 → GitHub fetcher → 安卓/后台 UI**。
