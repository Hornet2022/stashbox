# 文档剪藏 · 契约 v1（2026-10-23）

> 状态：**已实现（后端）**，安卓端 / 管理后台 / 改写 prompt 分支待做。
> 本文是「缝合定义」—— 后面几端的改动都按这里打补丁，不要各自发明。

## 0. 一句话

**文档剪藏 = 用户提交一份文档（文件或粘贴文本）→ 解析成与抓取同形的正文 → 走**现有剪藏链路**的后半程。**

关键设计：**`articles.raw_content` 的形状不变**（仍是 `FetchResult` 同形），
所以蒸馏、订阅推送、TTS 全链路**零改动**。

## 1. 为什么单独一个端点

现有 `POST /api/v1/articles` 的轴是 **URL**（`get_fetcher(url)` → 抓 → 建库）。
文档没有 URL。硬塞字段就要在链路中间插分叉，而分叉插在链路中间，
后面每一环都要记得「这次没有 fetcher 结果」。

所以分叉放在**链路之前**：

```
链接剪藏：URL → fetcher 抓 ─┐
                            ├→ 正文（FetchResult 同形）→ 去重 → 扣配额 → 建库 → 派蒸馏 → 失效缓存
文档剪藏：文件 → 解析器 ────┘
```

后半程**只有一份实现**（`_clip_after_fetch`）。

## 2. 端点契约

`POST /api/v1/articles/document`（multipart/form-data）

| 字段 | 类型 | 说明 |
|---|---|---|
| `file` | 文件（可选） | 文档二进制 |
| `text` | 文本（可选） | 直接粘贴的 Markdown / 纯文本 |
| `title` | 文本（可选） | 不填则从文档推断 |

* `file` 与 `text` **二选一**；都为空 → 400；都传 → 400。
* 响应与 `POST /api/v1/articles` 同形，另加 `reused` / `filename` /
  `content_type` / `text_length` 四个诊断字段。

### 与链接剪藏的语义对齐（逐条）

| 语义 | 链接剪藏 | 文档剪藏 | 共同实现 |
|---|---|---|---|
| 先拿正文后扣费 | 抓取失败 → 2002，不建库不计费 | 解析失败 → 2002，不建库不计费 | 同口径（2026-10-03 定的） |
| 去重 | 同 user + 同 url | 同 user + 同 **内容 hash** | `_find_existing_clip` |
| 扣配额 | 建库前 | 建库前 | `quota_service.consume` |
| 标记已扣费 | `mark_article_quota` | 同 | 同 |
| 派蒸馏 | `trigger_distill` | 同 | 同 |

## 3. `articles` 表：**不改**

| 列 | 文档剪藏怎么填 |
|---|---|
| `url` | `doc://{sha256[:16]}`（**内容 hash**）→ 同一份文档重复上传天然复用同一篇 |
| `source` | `"document"`（新码值，与 `web`/`wechat`/`pdf` 并列） |
| `title` | 请求的 title，否则从文档推断（文件名 → 首个 Markdown 标题 → 首个非空行） |
| `raw_content` | `FetchResult` 同形（`content_text` / `content_html` / `title` / `raw_metadata`） |
| `raw_content.raw_metadata` | 额外放 `filename` / `content_type` / `bytes` / `sha256` / `parser` / `text_length` / `truncated` / `page_count` |

**为什么不改表**：加列就要写 alembic 迁移，而新列对下游没有任何用处
（正文已经在 `raw_content` 里，且列表端点本来就把这列 defer 掉）。
不改表 = 零迁移风险。

**为什么 `url` 用内容 hash 而不是文件路径**：
`url` 有 NOT NULL 约束，而「同一份文档」的天然身份是**内容**不是文件名
（同一份 PDF 改名后仍是同一份）。用 hash ⇒ 去重语义正确，且不需要新列。

## 4. 支持的格式（第一版）

| 格式 | 解析方式 | 新依赖 |
|---|---|---|
| PDF | 复用 `fetchers.pdf.extract_pdf_text`（**与 PDF 直链抓取同一份逻辑**） | 无（pypdf 已有） |
| Markdown / TXT / CSV / JSON / YAML | 直接解码（utf-8 → gb18030 → 兜底 replace） | 无 |
| HTML | 复用 `fetchers.parser.ContentExtractor`（**与网页抓取同一份抽取器**） | 无 |
| DOCX | **标准库** `zipfile` + `xml.etree`（读 `word/document.xml` 的 `<w:t>` 节点，按 `<w:p>` 换行） | 无 |

**不支持**：扫描件 PDF（无文本层）、加密 PDF。→ 与现有 PDF 直链抓取**同样不支持**
（文档剪藏不该比「剪藏一个 PDF 链接」更宽松或更苛刻）。

> **为什么不引入 python-docx**：仓里除 pypdf 外没有第二个文档解析依赖，
> 而 DOCX 的正文抽取用标准库几十行就够。引入新依赖要过依赖评审，
> 收益不匹配。

## 5. 长度控制（两个维度）

| 维度 | 上限 | 超出时 |
|---|---|---|
| 上传文件大小 | **10MB** | 端点 400 + 明确文案（**与 nginx `client_max_body_size 10m` 同口径**） |
| 正文长度 | **200,000 字符** | **截断 + `raw_metadata.truncated=True` + warning 日志** |

* **文件上限必须与 nginx 一致**：端点比网关宽 → 用户先撞网关 413（没有信息量）；
  端点比网关窄 → 用户撞我们自己的提示（能说清为什么）。取 10MB，两边一致。
* **正文上限比网页的 50KB 大**：网页那个是「防爆」口径，文档是用户**特意**提交的
  内容，砍掉就是骗人。
* **截断必须可观测**：网页那侧是静默砍的（`parser.py` 的 50KB），
  文档不能这样 —— 用户会得出「这份文档没有我要的信息」的错误结论。

## 6. 错误话术

`fetch_error_user_message` 新增 `source == "document"` 分流：

* `PARSE` → 「没能从这个文档里读出文字。如果是扫描件（图片版 PDF）或加密文件，
  我们暂时读不了，可以换个文件或直接粘贴文本试试」
  （**不**沿用链接那句「页面可能需要登录」—— 文档没有「登录」这回事）
* `UNSUPPORTED` → 「暂时不支持这个文档格式，可以换个文件或直接粘贴文本试试」

>

> 服务端解析器。**白名单式过滤会再造一次同样的坑** —— 各设备对 `.md` 的 MIME
> 报告不一致（`text/markdown` / `text/plain`），未知后缀常是 `application/octet-stream`，
> 漏一项 = 用户的文件又灰了。
> 护栏：`DocumentPickerMimeTest`（断言传给选择器的每一项都含 `/`，
> 且每个支持的扩展名的真实 MIME 都能过客户端预检）。

### 8.3 改写 prompt 分支（**没有它，文档剪藏会出「胡话」**）

`_REWRITE_SYSTEM`（`ai-service/agent/runner.py:686-786`）现在假设输入是
「一篇公众号文章」，具体不适配：

| 契约点 | 原文 | 对文档/代码库的问题 |
|---|---|---|
| 任务定义 | 「把**原文**改写成…希望快速吃透**一篇文章**要点的人」 | 输入不是「一篇文章」 |
| hook | 「**钩子要狠**…可以是反问、矛盾、或出人意料的对比」 | 文档没有钩子感 → **逼出编造** |
| outro | 「**收束呼应**：呼应 hook 的开头意象」 | 文档无叙事线可呼应 |
| 不要复读 | 「**不要复读原文**，要重述 + 加你的解读」 | README 的价值恰恰是**准确复述**用法 → 与下面「有依据」自相矛盾 |
| 长度自适应 | 「> 2000 字 → 1000-1400 字」 | 文档常 5k-50k 字 → 与「不要漏点」**直接冲突** |
| 代码块 | 无「不要念代码块/命令/路径」的约束 | `pip install x` 会被念成「派 pip install」 |
| 标签 | 「必须从候选标签里原样选」 | 代码库主题（Python/数据库…）大概率不在 `tags` 表候选里 → **订阅推送彻底失效** |

⇒ 需要：按「素材类型」（文章 / 文档 / 代码库）分支 prompt；
`state["source"]` **已经在 initial_state 里**（`distill_task.py:924`），可直接用。

### 8.4 长文档的两个隐患

1. **max_tokens**：agent 改写**不传 max_tokens** → 吃默认 4096
   ⇒ 文档稿（1000-1400 字 + JSON 结构）**可能被截断成非法 JSON**
   → `_extract_json_object` 失败 → 降级成纯文本按空行切（稿子结构全丢）。

### 9.3 ✅ 已决：运营录入的内容**只靠订阅分发**（2026-10-24 产品拍板）

**决策原文**：

> 「admin 录入的内容对不对用户可见的问题，应该在用户 app 的订阅功能中
> 形成闭环，**订阅了分类就可以看到，没订阅就看不到**。」

⇒ 三层落地（**闭环在最后一环原本是断的**）：

| 层 | 改了什么 | 文件 |
|---|---|---|
| 读侧授权 | 新增 `_get_readable` / `_get_readable_with_task`：非属主时先问「订阅授权」。**10 个端点**切过去（详情 / status / audio-url / progress / listen-complete / rate / favorite / unfavorite / favorites / snooze） | `content-service/main.py` |
| 分类可靠 | `articles.manual_tags` 列（迁移 **0040**）+ admin 录入端点接受 `tags` + **蒸馏时运营指定的优先于 LLM 猜的** | `common/models/article.py`、`content-service/schemas.py`、`ai-service/tasks/distill_task.py` |
| 后台 | 录入抽屉加**分类多选**（候选来自 tags 表） | `stashbox-admin-web` |

**⚠️ 授权面是有边界的**：

* **只放行「消费 + 个人状态」类**：读稿、听音频、记自己的进度/评分/收藏/稍后听；
* **仍属主专属**：`skip`（写**共享列** `articles.skip`）、
  `mark-listened`（写**共享列** `articles.status`）、
  删除、重试蒸馏 —— 订阅者改一次会影响**所有人**。

**为什么闭环原本是断的**（值得记一笔）：
订阅流与推送**本来就不按 owner 过滤**（按分类分发），所以运营内容天然会出现在
订阅者的流里；但**读侧端点只认属主**（403）⇒ 用户点开就是「无权访问」。
⇒ 列表里有、点开没权限 —— 闭环断在最后一环。

**分类为什么必须可靠**：分类原先只有一条来源 —— **蒸馏时 LLM 猜的**。
实测 GitHub 开源库的稿子 `tags` 是**空的**（代码库主题大概率不在 tags 表候选里）
⇒ **永远进不了任何人的订阅流 = 死内容**，而且**没有任何报错**
（推送函数第一行就是 `if not da.tags: return 0`）。
所以运营录入时能**指定**分类，服务端优先用运营指定的。

**线上实测（2026-10-24）**：

| 场景 | 结果 |
|---|---|
| 运营录入并指定「科技」→ 订阅了科技的用户 | 订阅流里**能看到** ✓ 详情 **200** ✓ 音频 **200** ✓ |
| 同样内容但分类「财经」（用户没订阅） | 订阅流里**看不到** ✓ 详情 **403** ✓ 音频 **403** ✓ |
| 蒸馏落库 | `da.tags = ["科技"]` —— **等于运营指定的**，不是 LLM 猜的 ✓ |
| 订阅推送 | `push_notifications` 生成了 1 行（user 22 ← 科技那篇）✓ |

⚠️ **推送的「投递」还差一步**：生产没配 `STASHBOX_PUSH_WEBHOOK_URL`
（用户自己的推送网关）⇒ 通知行生成了但 `status=failed`、原因「未配置推送通道」。
**这是配置缺口，不是代码缺陷**；App 内的订阅流（订阅页的「订阅更新 N 篇」）
不依赖它。

**顺带修掉的一个静默失败**：同一份文档重复录入会命中内容去重（复用同一篇），
原先运营**新指定的分类被静默丢掉**（运营看到「创建成功」，内容却还挂在旧分类下）。
现在复用时**会更新分类**，且若该篇**已发布**就记一条 warning 说明
「要重新蒸馏才换分类」（`distilled_articles.tags` 是蒸馏时写的）。

缺段告警 `agent_rewrite_recreation_missing_part`：**0 条**。

产出的延伸判断长这样（文档那篇）：
「用内容 hash 做去重，前提是文件内容必须完全一致。哪怕只改了一个空格，
hash 就变了…意味着去重能力对『几乎一样但略有差异』的文档是失效的」
—— 从原文的「内容 hash 去重」推出了它的**失效边界**，这才是延伸判断该干的事。

### 9.2 延伸判断带来的新风险：**编造具体数字**（同轮发现并已加判据）

让「延伸判断」变成必填，代价是模型有机会顺手编一个**具体数字**。

实测（GitHub 那篇的延伸判断）：
「运行时懒加载子命令这个设计，在命令数量超过 **20 个**后收益才明显」——
而 README 里**根本没有 20**（只有 "lazy"）⇒ 听众会以为那是原文里的事实。

这类编造**最伤信任**：稿子其他部分都可以是「我们的看法」，
但一个看起来像原文事实的数字是**事实层面的造假**。

⇒ 加了机械判据 `recreation_quality.unsourced_numbers()`：
**条目里的数字必须在原文里找得到**（按数值相等判，宽松匹配）。
只告警不删内容（原文被截断时会有误判）——
告警事件 `agent_rewrite_unsourced_number`。
用生产上那条真实的延伸判断验过：准确命中 `['20']`，另一条不误报。

**同时澄清了技术方案里的红线**（不是推翻，是说清边界）：
「不做 AI 生成内容」指的是**不生成与原文无关的原创内容**（续写/扩写/换人称）；
关联思考/延伸判断/拓展方向是**基于原文**的判断（每句能追回原文的事实），
属于「蒸馏」不属于「生成」。见 `docs/技术方案_v2.md` §「❌ 4 · 不做 AI 生成内容」
下面的 2026-10-24 边界澄清。


## 10. GitHub 开源库剪藏 ✅（2026-10-24 已上线）

原判断「全仓零实现、零规划」仍然成立，方案就是上面写的那个：
`fetchers/github.py` 抓 README + 仓库元信息，`source="github"`，
复用现有整条 URL 剪藏链路。**实际落地的三个要点**：

1. **注册顺序**：`GitHubFetcher` 必须排在 `GenericURLFetcher`（catch-all）**之前** ——
   放后面就永远轮不到（`GitHubFetcher` 排在 `get_fetcher` 注册表里 `generic_url` 之上）。
2. **两条通道，raw 优先 / API 兜底**：生产实测 `raw.githubusercontent.com`
   **连不上**（10s 超时）、`api.github.com` **通**（0.6s）。
   ⚠️ 但 API 未认证限额是 **60 次/小时 / 共享出口 IP** ⇒ 内测规模够用，
   用户量上来会打光（响应头 `x-ratelimit-remaining` 可观测，**当前无告警**）。
3. **fetcher 内部必须走 `fetch_with_retry`**：初版直接 `client.get()`
   **绕过重试** ⇒ raw 偶发超时就整个剪藏失败。

**已知限制**：只抓 README（不读代码、不建依赖图谱）；仓库主题标签
（Python / 数据库…）大概率不在 `tags` 表候选里 ⇒ 贴不上标签 ⇒ 订阅推送对该来源失效
（prompt 已要求「不在就空数组，不要自造」—— 实测 GitHub 稿的 tags 就是空的）。

### 9.4 ✅ 已决：要 OCR（2026-10-24）

**决策**：文档剪藏要支持扫描件 PDF（用户明确要求，provider 侧有 OCR 模型）。

**路径是实测出来的，不是猜的**（provider = `https://tertu.cn/v1`，OpenAI 兼容）：

1. ❌ **PDF 不能直接喂模型** ——
   `data:application/pdf;base64,...` 被上游拒：
   `400 {"error":"Failed to load image: cannot identify image file"}` ⇒ 必须先转图片。
2. ✅ **零新依赖** —— 扫描件 PDF 本质是「一张张图片装在 PDF 里」，
   `pypdf` 的 `page.images` 能把内嵌图**原样**抽出来（零重编码、零画质损失）。
3. ✅ provider 的模型清单（`GET /v1/models`）里有两个能认字的：
   - `Qwen/Qwen3-VL-32B-Instruct` —— 输出**干净**、token 更省（270 vs 847）⇒ **默认用它**；
   - `deepseek-ai/DeepSeek-OCR-2` —— 专用 OCR 模型，但输出带 markdown 标记 ⇒ 备选。

⚠️ provider 上**没有** `qwen-vl-max` / `gpt-4o` 这两个名字（后台 tier 映射里写着，
实测 404 `Model not found`）⇒ **模型名要向 provider 现查**，不能照抄配置里的旧值。

**落地**：
- `backend/content-service/fetchers/ocr.py`（新）：抽图 → 逐张识图 → 拼文本；
- `parse_document_async()`（新）：「是 PDF 且文本层为空」才 OCR；
- `parse_document()`：加 `pdf_text` / `pdf_meta` 两个参数（同步核仍是唯一解析实现）；
- `PdfFetcher`（PDF 直链）：同样接上（同一类内容，同一条路）；
- 模型名可覆盖：`system_config.llm.ocr_model` → 环境变量 `STASHBOX_OCR_MODEL` → 默认值；
  base_url / api_key **复用 LLM 那份配置**（同一个 provider、同一个 key）。

**⚠️ 顺带改了文档的正文下限：200 → 80 字**
那个 200 是给**网页文章**定的（网页太短多半是导航页）。但扫描件天然短：
实测一页中文扫描件 OCR 出来 **161 字**（内容完全正确、连标点都对），
按 200 判就被拒 ⇒ 用户看到「没能从这个文档里读出文字」——
**明明读出来了却说没读出来**。80 字是「至少是一段完整的话」的下限。

**线上实测**（真机上传的中文扫描件 PDF）：

| 步骤 | 结果 |
|---|---|
| 上传扫描件 PDF | 200，`text_length=161`（中文全部识别正确） |
| 库里的正文 | 就是 OCR 出来的那段中文 ✓ |
| `raw_metadata` | `parser=pdf_ocr` · `ocr_model=Qwen/Qwen3-VL-32B-Instruct` · `ocr_images=1` · `ocr_errors=[]` ✓ |
| 蒸馏 | ready，737 字稿子 ✓ |

**护栏**：`tests/content/test_document_ocr.py`（9 例）—— 抽图 / 识图请求形态
（必须是 image_url 的 data URL）/ 元数据可观测 / 失败不阻断 / 有文本层不烧 OCR。

## 13. 稿子的篇幅与深度（2026-10-25 产品反馈「不够深刻、丰富」）

**反馈原文**：核心要点 / 关联思考 / 延伸判断 / 拓展方向，现在的内容不够深刻、丰富，
要提高内容质量和篇幅。

### 13.1 先量：卡住的是「条数」，不是「每条字数」

生产 32 篇实测（`content_parts`）：

| 段 | prompt 旧规格 | 生产实测每条字数 | 生产实测条数/篇 | 生产整稿字数 |
|---|---|---|---|---|
| sections（正文要点） | 80-160 字，共 3-5 节 | 均值 123（max 219） | 4.1 节 | — |
| related（关联思考） | 45-80 字，1-2 条 | 均值 111（max 147） | **1.47 条** | 中位 1150 字 |
| insights（延伸判断） | 50-100 字，2-3 条 | 均值 105（max 145） | 2.2 条 | 上限 1642 字 |
| follow_ups（拓展方向） | 45-80 字，1-2 条 | 均值 95（max 124） | **1.4 条** | 下限 793 字 |

⇒ **每条的字数早就超出规格**（模型自己写得更饱满）；真正被卡住的是
**条数**和**整稿字数闸门**（prompt 第 10 条把整稿钉在 1000-1400 字）。
⇒ 「不够丰富」是**被规格卡住的**，不是模型写不动。

### 13.2 实验：不改生产代码的新旧规格对照

生产上跑同一篇原文（`Qwen3.8-27B`，走仓库自己的 LLM 客户端）：

| | 整稿字数 | related/insights/follow_ups | 判据合格 |
|---|---|---|---|
| 旧规格 | 1308 字 | 2 / 3 / 2 | 7/7 |
| 新规格 | **1866 字（+43%）** | 3 / 4 / 3 | **8/10** ⚠️ |

⇒ 篇幅确实涨了，但**多出来的条目里混进了选题短语**
（「关注X的部署进度」「追踪Y的里程碑」——`no_reasoning`）。
⇒ **单纯「写更多」会把「浅」一起放大** —— 深度只能靠**把不合格的换掉**拿到。

### 13.3 落地：规格 ↑ + 补救（局部重写）

| 改什么 | 在哪 | 口径 |
|---|---|---|
| 篇幅阶梯 | `_REWRITE_SYSTEM` 第 10 条 | <500 字 → 900-1200；500-2000 → 1400-1900；>2000 → **1900-2600** |
| 条数下限 | `_REWRITE_SYSTEM` 的 JSON 契约 | sections 4-6 节；related **2-3** 条；insights **3-4** 条；follow_ups **2-3** 条 |
| 「具体性」硬要求 | `_REWRITE_SYSTEM` 第 11 条（新增） | 每条都要落到具体对象（公司/产品/协议/版本号/数字/时间），不许停在「行业」「生态」「趋势」 |
| 条数下限（判据） | `recreation_quality.MIN_ITEM_COUNTS` | related 2 / insights 3 / follow_ups 2 |
| 分段字数下限（判据） | `recreation_quality.MIN_CHARS_BY_PART` | related 60 / insights 70 / follow_ups 60（取生产实测最小值下方一点点） |
| 补救 | `runner._remediate_recreation` + `_apply_remediation` | 局部重写不合格条目 + 补齐条数；**失败只记不丢** |

⚠️ **补救必须把条数写进 prompt**：实测不写条数时，模型只重写不合格的那几条，
**不会顺手补齐条数** ⇒ 补齐落空，补救只做了一半。

⚠️ **max_tokens 不是瓶颈**：实测 completion_tokens 795~1111（整稿 1300~1900 字），
离 8192 很远 ⇒ 不需要为「更长」抬上限；真正的截断风险在**超长文档**那一侧。

### 13.4 篇幅下限是**软约束** ⇒ 也要变成硬判据

上线后用 uid=23 报障那篇实测（原文 8578 字）：新稿 **1783 字**，
比规格下限（>2000 字原文 → 1900-2600 字）**还低 12%**。

⇒ prompt 里写「1900-2600 字」模型**不保证照做**。要让它成立，
得有一条机械判据：

| 改什么 | 在哪 | 口径 |
|---|---|---|
| 字数阶梯（代码常量） | `recreation_quality.TARGET_CHARS_BY_SOURCE_LEN` | 与 prompt 第 10 条一一对应：900-1200 / 1400-1900 / 1900-2600 |
| 差额折算条数 | `recreation_quality.chars_shortfall` | `(差额, 还差几条)`；一条按 110 字估 |
| 触发条件 | `runner._remediate_recreation` | 弱条目 **或** 条数不足 **或** 字数不足 ⇒ 补救 |

⚠️ **字数口径必须含正文要点**：prompt 的阶梯是「四段合计」，
判据若只算三段 = 拿三段比四段的下限 ⇒ 差出一个正文的量 ⇒ 补救被误触发。

**护栏**：`tests/ai/test_recreation_depth.py`（21 例）—— 丰度判据 / 篇幅判据 /
补救合并规则（替换、保留、只记不丢）/ 补救失败与不解析都不崩 /
**规格不许悄悄退回旧值**（断言 prompt 里的篇幅阶梯与条数）。

## 14. 正文配图识图（图表改造档，2026-10-25）

### 14.1 问题：图表里的数字在链路里被**物理丢掉**

剪藏一个链接时，正文里的**图表 / 配图**会整个消失：文本化只收文本节点，
`<img>` 没有文本节点 ⇒ 图不在 `content_text` 里；而图表里的数字
**恰恰是"用图表讲数据"这类文章的全部信息量**。

⇒ 做法：文本化时留**占位符** `\x00IMG{n}\x00` → 抓完正文后**下载 + 识图**
→ 把占位符**原位**替换成图注；失败的**直接删掉**，不留任何残迹。

### 14.2 契约（判据在代码常量里，能查、能改、能反驳）

| 改什么 | 在哪 | 口径 |
|---|---|---|
| 占位符 | `media_ocr.make_token` | `\x00IMG{n}\x00`（NUL 哨兵，不与正文文字碰撞；落库前换可见记法，JSONB 不接受 `\u0000`） |
| **上限** | `media_ocr.MAX_MEDIA_CAPTIONS` | **12 个不同的图 URL**（⚠️ 不是"图片位置数"） |
| **去重** | `media_ocr._group_by_url` | 同一 URL 只 OCR **一次**，图注**复制**给它的每个占位符 |
| **零信息判据** | `media_ocr._is_zero_info` | 只认「**明确声明**图中没有文字」，**不认启发式** |
| **补位** | `media_ocr.caption_media` 的补位轮 | 最多 **1 轮**、总尝试 **≤ 2×上限**、预算耗尽**不补** |
| 图注前缀 | `media_ocr.CAPTION_PREFIX` | 「图表：」——与 prompt 教模型认的**必须是同一个前缀** |
| 并发 / 队列 | `MEDIA_OCR_CONCURRENCY` / `MEDIA_OCR_GLOBAL_CONCURRENCY` / `MEDIA_OCR_QUEUE_SIZE` | 单篇 3 / 全进程 6 / 队列 3（内存闸门：服务 MemoryMax=176M） |
| 超时 / 大小 | `MEDIA_DOWNLOAD_TIMEOUT` / `MEDIA_OCR_TIMEOUT` / `MAX_MEDIA_BYTES` | 15s / 15s / 5MB；且**取抓取总预算的剩余**（剪藏总时限 30s 是硬约束） |

### 14.3 零信息判据：形状来自**生产实测**，且有**反例集**

先量形态再写判据（生产 sspai 47 张图）：

- **该丢的形态**：`图中无文字与数字内容。`（6 个位置命中，但只对应 **2 个不同 URL**
  —— 那两张图各出现 3 次）⇒ 判据必须认**并列对象**（"文字**与数字**"），
  只写「图中没有文字」会漏掉主流形态；
- **不该丢的反例**（真**有**文字，启发式会误杀）：
  `10 小米10 新品直播发布会`、`为小米汽车而战`、
  `红色圆形背景中有一个白色的希腊字母π`、`高端是小米发展的必由之路，更是生死之战！`。

⇒ 判据 = 整条结果归一化（去空白与标点）后**整体**匹配声明本体
+ 尾巴只能是"没有实质内容"的同义改写 + 长度上限 40。
**不用**长度 / 画面描述 / 尺寸启发式 ⇒ 宁可放过一点噪音，也不能把**内容**删了。

### 14.4 生产实测（真实剪藏 + 落库核对，sspai 47 图文章）

| | 旧口径（上限按**位置**） | 新口径（按**不同 URL** + 零信息判失败 + 补位） |
|---|---|---|
| 图位置 / 不同 URL | 47 / 43（同一 URL 重复出现 3 次，白识 2 次） | 47 / 43 |
| 实际 OCR 尝试 | 12 次 | **14 个 URL**（12 + 补位 2） |
| 正文里的图注 | 12 条，其中 **6 条是"图中无文字与数字内容。"**（一半是垃圾） | **12 条全是真内容**，零信息 **0 条**进正文 |
| 剪藏耗时 | — | **20.3s**（预算 30s） |

其它两类来源（同一口径探针）：微信 16 图文章 → 14 位置 / **12 条真图注** / 18.0s；
solidot 7 图 → 5 条真图注 + 2 条零信息（**没有更多图可补 ⇒ 补位不发生**）/ 7.2s。

### 14.5 prompt 侧口径

`ai-service/agent/runner.py` 的 `_REWRITE_SYSTEM` 第 12 条告诉模型：
「图表：」是**配图里读出的文字、是素材不是正文**；画面描述/装饰要丢；不确定就丢。
⇒ 实测 8 次 LLM 调用，装饰污染 **0 次**（"模型恰好没写"是观察，不是契约 ——
第 12 条的价值在**确定性**）。

**护栏**：`tests/content/test_media_ocr.py`（32 例，含去重 / 零信息判据**反例集** /
补位闸门 / 预算耗尽不补 / Referer 请求级）+ `tests/ai/test_media_caption_prompt.py`（6 例，
前缀与 prompt 必须是同一个）。
